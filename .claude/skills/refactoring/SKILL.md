# 리팩토링 컨벤션

여러 번에 걸쳐 구현하거나 몇 번을 다시 뜯어고쳐도, 코드를 읽고 유지보수하는 데
어려움이 없는 상태를 유지하는 것이 목적이다.

각 절은 **규칙**과 **위반 판정**으로 되어 있다. 위반 판정에 걸리면 고친다.
"완벽히", "명확히", "견고히" 같은 말로 통과시키지 않는다.

---

## 1. 모듈 경계

### 규칙

- 디렉토리 하나가 모듈 하나로 책정된다. 모듈은 하나의 도메인 책임만 가진다.
- 비슷한 함수는 하나의 기능 파일로 묶는다. 함수 하나짜리 파일은 만들지 않아야하나, 대체나 병합이 어려운 함수의 경우 예외적으로 허용한다.
- 파일 하나가 단독으로 테스트된다.
- 디렉토리 내의 파일끼리는 직접 참조해 응집도를 올린다.
- 모듈 간에는 직접 참조하지 않는다.
- 호출 순서를 정하는 시퀀스 파일을 모듈마다 하나 둔다(`pipeline` 등 이름은 프로젝트마다의 규약을 따른다).
  기능 파일은 State를 들고 있지 않고, 시퀀스 파일이 state를 정의하고 조절한다.
  같은 입력이면 동작 흐름의 어느 위치에서 호출하더라도 같은 출력이 나와야 한다.

### 위반 판정

- 다른 모듈 디렉토리의 파일을 직접 import 하고 있는 경우
- 기능 파일이 모듈 레벨의 가변 state(전역 변수, 캐시, 카운터)를 포함하고 있는 경우
- 기능 파일에 함수가 하나 뿐이며, 해당 함수가 아직 다른 기능 파일과 병합할 수 있는 상태인 경우
- 모듈에 시퀀스 파일이 없어 호출 순서가 호출하는 측 책임으로 흩어져있는 경우

## 2. 통신

### 규칙

- 모듈 간 통신은 **message broker 기반 event bus**로 한다. 서로를 직접 호출하지 않는다.
- 시스템 외부(client, 외부 시스템)와의 통신은 **gateway** 한 곳으로 모은다.
  gateway는 진입점 역할만 하고 도메인 로직을 갖지 않는다.
- 내부 통신(broker)과 외부 진입(gateway)은 서로 대체하지 않는다.
  모듈끼리 gateway를 경유하지 않고, 외부 요청이 broker로 직접 들어오지 않는다.
- interface는 기대 입력과 기대 출력이 확정된 형태여야 한다.
  수신 측이 송신 측 내부 사정을 알아야 해석되는 값은 interface가 아니다.

**예외 — 요청 하나에 응답 하나를 기다려야 하는 통신은 직접 호출한다.**
사람이 묻고 답을 기다리는 자리가 그렇다. broker 로 흘리면 답을 받을 자리가 없어진다.
이때도 규칙 셋을 지킨다.

- 부르는 쪽은 **gateway 하나**로 제한한다. 모듈끼리 서로 직접 부르지 않는다.
- 주소는 환경변수로 넣는다. 부르는 쪽 코드에 박지 않는다.
- 부르는 쪽에 timeout 과 실패 시 동작을 둔다. 응답을 무한정 기다리지 않는다.

이 예외를 쓰는 자리를 세어 둔다. 늘어나면 경계를 잘못 나눈 것이다.

### 공유해도 되는 것 / 안 되는 것

메시지 규격(field 이름과 타입)은 **한 세트만 두고 모든 모듈이 그것을 참조한다.**
각자 복사해 두면 한쪽이 field를 바꿀 때 다른 쪽이 조용히 어긋난다.

공유 규격 파일에는 **선언만 둔다.** 계산·판단·분기가 들어가면 그때부터 기능 코드이고,
기능 코드는 절대 공유하지 않는다.

| | 공유 |
|---|---|
| message·event field 정의, 상수, subject 이름 | 한 세트 |
| 여러 모듈이 같은 값을 참조해야 하는 데이터 | 한 세트 |
| 계산·판단·변환하는 함수 | 각자 |

### 규격 변경 절차

구현을 먼저 바꾸고 규격을 나중에 맞추지 않는다. 규격이 먼저다.

1. 규격 파일을 고친다
2. 참조 측 타입·mock을 다시 만든다
3. 송신 측과 수신 측 구현을 고친다
4. 양쪽을 **같은 규격 파일 기준으로** 검증한다

각자 자기 테스트를 통과했는지가 아니라, 양쪽이 같은 규격을 통과했는지가 기준이다.

- field 추가는 호환된다. 기존 참조 측이 그대로 도는지만 확인한다.
- field 이름 변경·삭제·타입 변경은 breaking change다. 기존 field를 조용히 다른 의미로
  재사용하지 않는다. 새 이름을 추가하고 옮긴 뒤 옛 것을 제거한다.
- 타입 검사 통과로 끝내지 않는다. **실제로 직렬화된 값**으로 확인한다.
  DB 드라이버나 언어의 숫자 변환이 값을 바꿔 놓는 경우는 타입 검사에 안 걸린다.
- 검증에 포함할 경로 — 정상, 문서화된 오류 각각, 빈 컬렉션, nullable field.

### 위반 판정

- 모듈 A가 모듈 B의 함수를 직접 호출하고 있는 경우
- gateway 가 아닌 모듈이 다른 모듈을 직접 호출하고 있는 경우
- 직접 호출하는 자리에 timeout 이나 실패 시 동작이 없는 경우
- 같은 메시지의 field 이름이 두 곳 이상에 각각 선언되어 있는 경우
- field 이름이 어긋나는지 감시하려고 문자열을 하드코딩한 테스트가 있는 경우
  (규격이 한 세트가 아니라는 뜻이다. 합치면 그 테스트는 필요 없어진다)
- 공유 규격 파일에 조건문이나 계산이 포함되어 있는 경우
- gateway가 도메인 판단을 하고 있는 경우
- 구현을 먼저 바꾸고 규격 파일을 나중에 맞춘 경우
- 규격에 없는 field를 참조 측이 쓰고 있는 경우
- 기존 field의 의미만 바꿔 재사용한 경우

## 3. 테스트로 분리를 증명한다

### 규칙

- 모듈의 분리는 **단위테스트가 증명한다.** 그 모듈만으로 자기 책임을 재현할 수 있어야 한다.
- 단위테스트는 상대를 실제로 호출하지 않는다. 응답을 mock으로 세운다.
  확인하는 것은 **규약대로 호출했는가**와 **응답을 규약대로 해석했는가**다.
  상대가 죽었을 때 내 단위테스트가 깨지면 그것은 단위테스트가 아니다.
- 테스트는 세 계층으로 둔다 — 파일 단위, 모듈 단위, 모듈을 연결한 통합.
- 외부와 실제로 통신하는 검증은 통합테스트에 두고 단위테스트와 섞지 않는다.

### 위반 판정

- 단위테스트가 네트워크, 파일시스템, DB, 외부 API에 실제로 닿고 있는 경우
- 다른 모듈을 기동해야만 통과하는 테스트가 단위테스트 위치에 있는 경우
- 모듈에 자기 테스트가 없는 경우

## 4. 장애 격리

### 규칙

- 한 모듈의 장애가 다른 모듈로 전파되지 않는다.
- 모듈은 각자의 컨테이너에서 돈다.
- 의존 대상의 응답을 기다리는 모든 지점에 **timeout과 retry 상한**이 있다.
  기본값에 맡기지 않는다. 기본값은 대개 무한이거나 분 단위다.
- 의존 대상이 없을 때의 동작을 정한다 — drop할지, queue에 쌓을지, 자기도 멈출지.
  정하지 않으면 hang 상태로 남는다.

### 위반 판정

- connect·호출에 timeout이 지정되지 않은 경우
- retry가 상한 없이 반복되는 경우
- 의존 대상이 죽었을 때의 동작이 코드에 정의되어 있지 않은 경우
- 한 모듈이 죽으면 전체가 멈추는 경우

## 5. Health check

### 규칙

장애를 조기에 격리하려면 health check가 **실제 상태를 반영해야 한다.**
"살아 있다"만 반환하는 health check는 아무것도 막지 못한다.

반드시 포함할 것:

- 의존 대상마다 **실제로 연결되었는지** 각각 (broker, DB, 모델 서버, 외부 API)
- 실패했으면 **어느 의존 대상에서 실패했는지**
- 기동에 필요한 준비가 끝났는지 (모델 load, migration 등)
- health check 자체가 오래 걸리지 않을 것. health check가 hang하면 그것이 장애가 된다

### 위반 판정

- health check가 고정된 값만 반환하는 경우
- 의존 대상이 끊겼는데 health check가 정상을 반환하는 경우
- connect 실패가 로그에도 health check에도 남지 않는 경우

## 6. 실행환경 분기

### 규칙

- Dev, Test, Release, Demo는 **같은 파이프라인을 쓰고 설정으로 분기한다.**
  환경마다 설정 파일 전체를 복제하지 않는다.
- **Release 설정을 base 파일로 둔다.** 다른 환경은 base 위에 override한다.
  base를 Dev로 두면 표시를 누락한 것이 현장에 나가고,
  Release로 두면 개발 머신에 하나 더 뜨는 것으로 끝난다.
- 환경마다 다른 값은 환경변수로 분리한다. 코드나 설정 파일에 하드코딩하지 않는다.
- 특정 환경에만 필요한 모듈은 profile로 켜고 끈다.
- 환경 전용 기능도 interface를 통해 붙인다. 환경 전용 통신 경로를 따로 만들지 않는다.

### 위반 판정

- 환경별 설정 파일이 서로의 복사본인 경우 (한쪽에 field를 추가하면 다른 쪽에도 추가해야 하는 상태)
- base에 있는 설정값이 다른 환경 파일에 누락되어 그 환경에서 변경할 수 없는 경우
- Demo나 Test 전용 코드가 Release 코드 안에 조건문으로 섞여 있는 경우

## 7. 주석

### 규칙

WHAT과 WHY를 쓰는 위치가 다르다.

**기능 파일 — WHAT을 적는다.**
어느 함수에 어떤 값을 넣어 무엇이 나오는지. 시퀀스가 한눈에 보여야 한다.
왜 이렇게 구현했는지는 여기 적지 않는다.

**시퀀스 파일 — 호출부에 WHY를 적는다.**
그 기능이 이 위치에 배치된 이유가 곧 WHY다.
앞 단계의 무엇을 받아야 하는지, 왜 이 순서여야 하는지를 호출하는 줄에 적는다.

```python
# 기능 파일 - WHAT
def denoise(frames: bytes) -> bytes:
    # frames 를 RNNoise 에 넣어 잡음이 제거된 PCM 을 돌려준다

# 시퀀스 파일 - 호출부에 WHY
pcm = denoise(frames)   # STT 이전에 둔다. 잡음이 남으면 오인식이 교정 단계에서 안 잡힌다
text = transcribe(pcm)
```

- 코드를 그대로 다시 쓴 주석은 쓰지 않는다.
- 놓치기 쉬운 문법·연산자는 상세히 적는다. 이것은 예외다.
- 형식(single line / multi line)은 제한하지 않는다. 다만 주석이 길어지면
  시퀀스가 아니라 서술을 쓰고 있다는 신호다.
- 검토 과정과 변경 이력은 어느 쪽에도 적지 않는다. 개발일지나 커밋 메시지에 적는다.
- 개발 용어를 임의의 한글 단어로 치환하지 않는다.
  UI·백엔드·CPU·GPU·API를 판·뒷단·처리기·그림작가·메뉴판 따위로 옮기지 않는다.
  반대로, 설명이 필요한 자리에 파일명과 함수명만 나열하지도 않는다.

```python
# 나쁨 - 코드를 그대로 옮겼다
i += 1  # i를 1 늘린다

# 나쁨 - 배경 서술이다
# 처음에는 여기서 바로 처리했는데 성능 문제가 있어서 큐를 거치도록 바꿨다.
# 다른 방법도 검토했지만 이 방식이 가장 안정적이라고 판단했다.

# 좋음 - 시퀀스다
# frames 를 preprocess 에 넣어 denoise 된 PCM 을 받고, 그것을 STT 에 넘긴다

# 좋음 - 놓치기 쉬운 연산자는 상세히
print(*L)  # 변수 앞의 * 는 포인터가 아니라 unpacking 연산자다.
           # ["1", "2"] 를 대괄호·따옴표 없이 1 2 로 출력한다.
```

### 위반 판정

- 주석이 바로 아래 코드 한 줄을 한국어로 옮긴 것에 불과한 경우
- 기능 파일에 배치 이유·설계 배경이 적혀 있는 경우
- 시퀀스 파일 호출부에 WHY가 없어, 순서를 바꿔도 되는지 판단할 수 없는 경우
- 주석에 검토 과정·변경 이력이 들어 있는 경우
- 개발 용어가 임의의 한글 단어로 치환되어 있는 경우

## 8. 읽기 쉬운 코드

혼자 개발하더라도 동료 개발자, 또는 인계받을 다음 개발자가 읽는다는 전제로 쓴다.

### 규칙

- 컴프리헨션은 **가독성이 나아질 때만** 쓴다.
  단일 결과, 단일 출처, 단일 반복, 단일 조건일 때가 그 경우다.
  중첩되거나 조건이 여럿이면 풀어 쓴다.
- 값 하나에 두 가지 의미를 담지 않는다. 처음부터 분리해서 받는다.
- 디버거를 붙여야만 파악되는 지점을 남기지 않는다.
- 불필요하게 늘려 쓰지도 않는다. 기초적인 축약까지 풀면 그것도 가독성을 해친다.
- 언어가 제공하는 표준 구문을 쓴다. index로 순회하며 원소를 꺼내는 반복문을 직접 만들지 않는다.

```python
# 값 하나에 두 의미 - port가 없을 수 있다
ip_and_port = input()   # "192.168.0.1:8000" 을 기대하지만 "192.168.0.1" 이 올 수 있다

# 분리해서 받는다
ip = input()            # "192.168.0.1"
port = input()          # "8000"
ip_and_port = f"{ip}:{port}"

# 불필요하게 늘렸다
if x > 5:
    return True
else:
    return False

# 이 정도 축약은 가독성을 해치지 않는다
return x > 5
```

### 위반 판정

- 하나의 입력값을 나중에 분해해서 쓰는데, 그 형태로 들어온다는 보장이 없는 경우
- 컴프리헨션에 조건이 둘 이상이거나 컴프리헨션이 중첩되어 있는 경우
- `if 조건: return True / else: return False` 형태가 있는 경우
- 언어에 enumerate 계열 구문이 있음에도 index range를 직접 만들어 배열을 순회하는 경우

## 9. 문서

- 소스코드와 문서를 분리한다.
- 문서는 내용·분량·개수 모두 필요한 만큼만 만든다.
- 임시 문서는 임시임을 문서 안에 명시하고, 쓰임이 끝나면 프로젝트가 정한 폐기 위치로 보낸다.
- 진행 상황만 담는 문서는 만들지 않는다. 그것은 커밋 이력에 있다.

## 적용 순서

1. 현재 코드가 어느 위반에 걸리는지 먼저 센다. 고치기 전에 목록을 만든다.
2. 모듈 경계(1절)부터 잡는다. 경계가 틀린 상태에서 통신을 정하면 두 번 고친다.
3. 모듈 하나를 분리하면 **분리 직후 실제로 기동해 확인한다.** 테스트만으로 넘어가지 않는다.
   여러 개를 분리해 놓고 한꺼번에 확인하면 어느 단계에서 깨졌는지 못 찾는다.
4. 모듈 경계를 넘을 때 증가하는 latency를 측정한다.
   프로젝트에 latency 목표가 있으면, 첫 모듈을 분리한 직후에 측정한다.
5. 네이밍 정리(같은 대상에 이름이 여럿인 경우)는 분리가 끝난 뒤에 한다.

## 하지 않는 것

- 위반을 발견하고 우회하지 않는다. 막히면 이유를 말하고 검토받는다.
- 중복 코드나 임시 코드로 넘기지 않는다.
- 결과를 확인하지 않고 되었다고 하지 않는다.
