# 2026-08-27 — 하네스 정리

## 왜 오늘 코드가 아니라 하네스를 먼저 건드렸나

한 달 만에 저장소를 열어 상태를 확인했습니다. 마지막 커밋이 2026-07-23이고,
로컬에만 있던 커밋 50개를 origin에 올렸습니다.

이어서 사람 목록·등록 endpoint(API 의 요청 주소 단위)부터 만들기로 하고 실패하는 테스트를 쓰려던 참에 멈췄습니다.
멈춘 이유는 작업이 아니라 규칙 쪽이었습니다.

- 명령을 하나 칠 때마다, 파일을 하나 만들 때마다 ECC의 GateGuard 훅이 사실 나열을 요구했습니다.
  2번 막혔고 그때마다 설명을 문단 단위로 써야 했습니다.
- 프로젝트 규칙(`CLAUDE.md`)이 지정한 `superpowers` 스킬 4개는 그 플러그인이 꺼져 있어
  하나도 부를 수 없었습니다. 규칙과 실제 설정이 어긋난 채로 한 달을 지나온 것입니다.
- 입력 토큰이 빨리 차고 속도가 느리다는 체감이 있었습니다.

## 결정한 것

**플러그인은 ECC 하나만 씁니다.** 규칙에서 superpowers를 삭제하고 ECC 에이전트·스킬로 교체합니다.

**전역과 프로젝트의 역할을 나눕니다.** `~/.claude/CLAUDE.md`는 어느 프로젝트에나 적용되는
범용 작업 방식이고, 저장소의 `CLAUDE.md`는 전역 규칙을 상속한 뒤 이 프로젝트에만 해당하는
규칙만 추가합니다. 그래서 프로젝트 파일에서 공통 규칙과 겹치던 절(소통 방식, 코딩 규칙,
보안, 커밋, 문서 형상관리)을 전부 제거했습니다.

**`PROGRESS.md`와 `TASK.md`를 폐지합니다.** 개발일지가 같은 일을 하고 있었습니다.
무엇을 했는지는 `git log`에 있고, 고민과 결정의 흐름은 개발일지에 있습니다.
아직 못 한 일은 개발일지 맨 끝 남은 것에 적습니다. 별도 파일을 만들지 않습니다.
`COMMAND.md`는 대체재가 없으므로 그대로 둡니다.

**기준은 PoC_Asterix 하네스로 잡습니다.** 그 저장소는 같은 방식으로 이미 정리해 둔 곳이라,
파일 배치·훅·스킬·문서 관리 범위를 최대한 같게 맞춥니다. 가져온 것은 3가지입니다.

- 삭제 금지 훅(`.claude/hooks/move-to-trash.ps1`) — 삭제 명령을 차단하고 `trash/`로 옮기게 합니다
- 리팩토링 스킬(`.claude/skills/refactoring/SKILL.md`)과 그 목적 문서(`refactoring.md`)
- 문서 관리 범위 구분 — cluedoc이 `.cluedoc/`과 `COMMAND.md`, ECC가 `README.md`,
  `CLAUDE.md`는 아무도 자동으로 건드리지 않습니다

**`PRODUCT_CONFIG.md`도 폐지합니다.** 기술 스택·코드 스타일·비밀값·커밋 형식은 `CLAUDE.md`가
하는 일과 같은 일이었고, 두 파일로 나뉘어 있으니 어느 쪽을 봐야 하는지가 매번 헷갈렸습니다.
유효한 내용을 `CLAUDE.md` 4·5·7·8장으로 옮기고 파일은 `trash/2026-08-27-harness-ecc/`로
보냈습니다. 기준 저장소인 PoC_Asterix에도 이 파일은 없습니다.

**다음 1차 목적은 리팩토링입니다.** 가져온 리팩토링 스킬의 위반 판정으로 현재 코드를 세고,
목록을 만든 뒤 모듈 경계부터 잡습니다.

## 검사를 사람 손에서 떼어내기로 한 이유

하네스를 정리하고 리팩토링에 들어가려는데, 첫 단계인 "위반 목록 만들기"가 문제였습니다.
소스 18개를 전부 문맥에 올려놓고 규칙 9절과 하나하나 대조하는 일입니다. 문맥이 꽉 차고,
다음에 또 검사하려면 처음부터 다시 해야 합니다.

그래서 스킬로 묶었습니다(`refactor-audit`). 서브에이전트 2개를 동시에 실행하고 결과만 받습니다.
파일 내용이 메인 대화에 안 올라옵니다.

**2가지 각도로 나눈 것이 핵심입니다.** 한 각도로는 놓칩니다.

- **리뷰어** — 규칙을 압니다. `refactoring` 스킬의 위반 판정으로 검사합니다.
- **러너** — 규칙을 모릅니다. 코딩을 갓 배운 신입으로서 막히는 지점마다 질문을 적습니다.

러너를 처음에는 "경력 있는 개발자가 이 코드를 처음 본다"로 잡았다가 뒤집었습니다.
사용자가 "러너는 learn 한다는 뜻"이라고 바로잡았습니다. 그 차이가 컸습니다. 처음 설계에서는
문법 질문과 라이브러리 질문을 제외하라고 적어 뒀는데, 그 지시가 정확히 반대였습니다.
`refactoring` 스킬 7절이 "놓치기 쉬운 문법·연산자는 상세히 적는다"를 예외로 명시해
뒀으니, 신입이 기호에서 막히는 자리가 곧 그 규칙을 안 지킨 자리입니다.

에이전트 2개 모두 규칙 문서와 설계 문서를 읽지 못하게 차단했습니다. 러너가 `.cluedoc/`를 읽으면
코드가 설명 안 해준 것을 문서에서 배워 와서 질문이 안 나옵니다.

## 판정을 뒤집은 것 — broker와 컨테이너

리뷰어가 2-1(broker 없이 직접 호출)과 4-4(한 프로세스)를 `과함`으로 판정했고,
저는 그 판정을 그대로 사용자에게 전달했습니다. 사용자가 "컨테이너랑 메시지브로커가
왜 과한데"라고 물어 다시 봤습니다.

**리뷰어의 판단 기준이 잘못되었습니다.** 소스가 1,300줄이라는 규모로 판단했는데,
기준은 그 코드가 무슨 일을 하느냐입니다. 그리고 `refactoring.md` 첫 번째 목적에
broker 기반 event bus가 이미 명시돼 있습니다. 사용자가 정해 둔 것을 리뷰어 판단으로
덮은 셈입니다.

실제 근거는 다음과 같습니다. CP-SAT solve는 CPU 바운드에 시간 상한이 없고, 배정 실패 시
사람 수만큼 반복됩니다. 지금 구조에서는 uvicorn worker 1개가 그 계산에 점유됩니다.
worker가 4개면 배정 요청 4개로 서버 전체가 응답을 중지하고 `/health`조차 못 받습니다.
solver가 메모리를 다 쓰고 종료되면 API도 같이 종료됩니다.

**가장 무겁고 가장 위험한 부분이 정확히 분리할 대상입니다.** 줄 수와 무관합니다.

2건을 `해당함`으로 수정하고 근거를 `AUDIT.md` 4부에 적었습니다.
남은 `과함`은 2건(TimeInterval 검증 위치, `range(len())` 3곳)이고 2건 다 유지하기로 했습니다.

- 팀별 합주량 자동 산정(운영시간 ÷ 팀 수) — 현재 `slots_per_team`을 외부에서 받습니다

### 백엔드 웹 계층 — 목록·등록 endpoint (다음 구현 후보)
현재 서버 주소는 5개뿐이고, 전부 "번호를 이미 알고 있을 때" 쓰는 것입니다. 그 번호를 사람이 선택할 수 있게 하는 endpoint가 하나도 없어, 지금은 DB를 직접 봐야 번호를 알 수 있습니다. 화면을 붙이려면 아래가 먼저 필요합니다.
- 기간: 목록 보기 / 추가 / 수정
- 팀: 목록 보기 / 추가 / 멤버 추가·삭제
- 합주실: 목록 보기 / 추가 / 운영시간 수정
- 사람: 목록 보기 / 등록 / 불가능시간 추가·삭제
