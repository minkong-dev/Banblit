# 2026-08-27 — 하네스 정리

## 왜 오늘 코드가 아니라 하네스를 먼저 건드렸나

한 달 만에 저장소를 열어 상태를 확인했다. 마지막 커밋이 2026-07-23이고,
로컬에만 있던 커밋 50개를 origin에 올렸다.

이어서 "사람 목록·등록 통로"부터 만들기로 하고 실패하는 테스트를 쓰려던 참에 멈췄다.
멈춘 이유는 작업이 아니라 규칙 쪽이었다.

- 명령을 하나 칠 때마다, 파일을 하나 만들 때마다 ECC의 GateGuard 훅이 사실 나열을 요구했다.
  두 번 막혔고 그때마다 설명을 몇 문단씩 써야 했다.
- 프로젝트 규칙(`CLAUDE.md`)이 지정한 `superpowers` 스킬 네 개는 그 플러그인이 꺼져 있어
  하나도 부를 수 없었다. 규칙과 실제 설정이 어긋난 채로 한 달을 지나온 것이다.
- 입력 토큰이 빨리 차고 속도가 느리다는 체감이 있었다.

## 결정한 것

**플러그인은 ECC 하나만 쓴다.** 규칙에서 superpowers를 걷어내고 ECC 에이전트·스킬로 갈아끼운다.

**전역과 프로젝트의 역할을 나눈다.** `~/.claude/CLAUDE.md`는 어느 프로젝트에나 적용되는
범용 작업 방식이고, 저장소의 `CLAUDE.md`는 그것을 상속한 뒤 이 프로젝트에만 해당하는
것만 얹는다. 그래서 프로젝트 파일에서 공통 규칙과 겹치던 절(소통 방식, 코딩 규칙,
보안, 커밋, 문서 형상관리)을 전부 뺐다.

**`PROGRESS.md`와 `TASK.md`를 폐지한다.** 개발일지가 같은 일을 하고 있었다.
무엇을 했는지는 `git log`에 있고, 고민과 결정의 흐름은 개발일지에 있다.
아직 못 한 일은 개발일지 맨 끝 "남은 것"에 적는다. 별도 파일을 만들지 않는다.
`COMMAND.md`는 대체재가 없으므로 그대로 둔다.

**기준은 PoC_Asterix 하네스로 잡는다.** 그 저장소는 같은 방식으로 이미 정리해 둔 곳이라,
파일 배치·훅·스킬·문서 관리 범위를 최대한 같게 맞춘다. 가져온 것은 세 가지다.

- 삭제 금지 훅(`.claude/hooks/move-to-trash.ps1`) — 지우는 명령을 막고 `trash/`로 옮기게 한다
- 리팩토링 스킬(`.claude/skills/refactoring/SKILL.md`)과 그 목적 문서(`refactoring.md`)
- 문서 관리 범위 구분 — cluedoc이 `.cluedoc/`과 `COMMAND.md`, ECC가 `README.md`,
  `CLAUDE.md`는 아무도 자동으로 건드리지 않는다

**`PRODUCT_CONFIG.md`도 폐지한다.** 기술 스택·코드 스타일·비밀값·커밋 형식은 `CLAUDE.md`가
하는 일과 같은 일이었고, 두 파일로 나뉘어 있으니 어느 쪽을 봐야 하는지가 매번 헷갈렸다.
살아 있는 내용을 `CLAUDE.md` 4·5·7·8장으로 옮기고 파일은 `trash/2026-08-27-harness-ecc/`로
보냈다. 기준 저장소인 PoC_Asterix에도 이 파일은 없다.

**다음 1차 목적은 리팩토링이다.** 가져온 리팩토링 스킬의 위반 판정으로 현재 코드를 세고,
목록을 만든 뒤 모듈 경계부터 잡는다.

## 검사를 사람 손에서 떼어내기로 한 이유

하네스를 정리하고 리팩토링에 들어가려는데, 첫 단계인 "위반 목록 만들기"가 문제였다.
소스 18개를 전부 문맥에 올려놓고 규칙 9절과 하나하나 대조하는 일이다. 문맥이 꽉 차고,
다음에 또 검사하려면 처음부터 다시 해야 한다.

그래서 스킬로 묶었다(`refactor-audit`). 두 서브에이전트를 동시에 띄우고 결과만 받는다.
파일 내용이 메인 대화에 안 올라온다.

**두 각도로 나눈 것이 핵심이다.** 한 각도로는 놓친다.

- **리뷰어** — 규칙을 안다. `refactoring` 스킬의 위반 판정으로 훑는다.
- **러너** — 규칙을 모른다. 코딩을 갓 배운 신입으로서 막히는 지점마다 질문을 적는다.

러너를 처음에는 "경력 있는 개발자가 이 코드를 처음 본다"로 잡았다가 뒤집었다.
사용자가 "러너는 learn 한다는 뜻"이라고 바로잡았다. 그 차이가 컸다 — 처음 설계에서는
문법 질문과 라이브러리 질문을 빼라고 적어 뒀는데, 그게 정확히 반대였다.
`refactoring` 스킬 7절이 "놓치기 쉬운 문법·연산자는 상세히 적는다"를 예외로 못 박아
뒀으니, 신입이 기호에서 막히는 자리가 곧 그 규칙을 안 지킨 자리다.

두 에이전트 모두 규칙 문서와 설계 문서를 못 읽게 막았다. 러너가 `.cluedoc/`를 읽으면
코드가 설명 안 해준 것을 문서에서 배워 와서 질문이 안 나온다.

## 판정을 뒤집은 것 — broker와 컨테이너

리뷰어가 2-1(broker 없이 직접 호출)과 4-4(한 프로세스)를 `과함`으로 판정했고,
나(클로드)는 그것을 그대로 사용자에게 전달했다. 사용자가 "컨테이너랑 메시지브로커가
왜 과한데"라고 물어 다시 봤다.

**리뷰어의 판단 기준이 틀렸다.** 소스가 1,300줄이라는 규모로 판단했는데,
기준은 그 코드가 무슨 일을 하느냐다. 그리고 `refactoring.md` 첫 번째 목적에
broker 기반 event bus가 이미 명시돼 있다 — 사용자가 정해 둔 것을 리뷰어 판단으로
덮은 셈이다.

실제 근거는 이렇다. CP-SAT solve는 CPU 바운드에 시간 상한이 없고, 배정 실패 시
사람 수만큼 되풀이한다. 지금 구조에서는 uvicorn 워커 하나가 거기 붙잡힌다.
워커가 4개면 배정 요청 4개로 서버 전체가 멎고 `/health`조차 못 받는다.
solver가 메모리를 다 쓰고 죽으면 API도 같이 죽는다.

**가장 무겁고 가장 위험한 부분이 정확히 떼어낼 대상이다.** 줄 수와 무관하다.

두 건을 `해당함`으로 고치고 근거를 `AUDIT.md` 4부에 적었다.
남은 `과함`은 2건(TimeInterval 검증 위치, `range(len())` 세 곳)이고 둘 다 유지하기로 했다.

검사는 끝났다(`AUDIT.md`). 다음은 무엇을 고칠지 고르는 것이다.

- **3절부터 8절까지 아직 사용자와 함께 안 봤다.** 1절·2절만 항목별로 짚었다
- 결정 필요: 배정 요청을 비동기(접수 → 작업 번호 → 조회)로 바꿀지. broker로 쪼개면 따라오는 결정이고, 화면 설계가 달라진다
- 고칠 후보 세 개 — CP-SAT solver 시간 상한 / 이름 필드에 두 정보 싣기 / health check가 고정 문자열
- 쪼갠다면 gateway·scheduler·store 세 경계. 분리 직후마다 실제로 기동해 확인한다
- 러너 질문 139건 중 90건은 주석으로 해결된다 — 구조 정리가 끝난 뒤에 붙인다

### 결정이 필요한 것
- 배정 실패 시 예약 가능 자리를 어떻게 볼지 — 현재는 빈 목록으로 반환. "자동 배정이 실패했으니 모든 칸이 비어 있다"로 볼지 판단 필요
- 팀별 합주량 자동 산정(운영시간 ÷ 팀 수) — 현재 `slots_per_team`을 외부에서 받음
- 같은 개수 강제 조건의 유연화 여부 검토(부분 충족 허용 등)
- 배정에 시간 선호를 넣을지 — 현재 조건만 맞으면 아무 칸이나 고름(밤 11시와 저녁 7시를 동등하게 취급)
- 팀에 소속된 멤버가 탈퇴할 때, 그 파트의 대체자를 헤드매니저에게 알려 지정받는 절차(알림 기능이 생긴 뒤 구현)
- 날짜가 겹치는 두 집중기간이 **같은 팀**을 쓰면, 그 팀이 같은 시각에 두 합주실에 배정될 수 있다. 저장 제약은 같은 합주실일 때만 걸러 준다. 집중기간이 겹치는 것 자체를 막을지, 배정할 때 다른 기간의 확정분까지 볼지 정해야 한다

### 백엔드 웹 계층 — 목록·등록 통로 (다음 구현 후보)
현재 서버 주소는 5개뿐이고, 전부 "번호를 이미 알고 있을 때" 쓰는 것이다. 그 번호를 사람이 고를 수 있게 하는 통로가 하나도 없어, 지금은 DB를 직접 봐야 번호를 알 수 있다. 화면을 붙이려면 아래가 먼저 필요하다.
- 기간: 목록 보기 / 만들기 / 고치기
- 팀: 목록 보기 / 만들기 / 멤버 넣고 빼기
- 합주실: 목록 보기 / 만들기 / 운영시간 고치기
- 사람: 목록 보기 / 등록 / 불가능시간 넣고 빼기
