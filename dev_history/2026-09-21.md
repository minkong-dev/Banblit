## 용어

| 말 | 뜻 |
|---|---|
| Referer | 브라우저가 요청을 보낼 때 "어느 페이지에서 왔는지"를 알리는 요청 헤더. 철자에 r 이 하나입니다(규격의 오타가 굳은 것) |
| Referrer-Policy | 그 Referer 를 어디까지 붙일지 정하는 응답 헤더. 철자에 r 이 둘입니다 |
| same-origin | Referrer-Policy 의 값 하나. 같은 출처로 가는 요청에만 Referer 를 붙이고, 다른 출처로는 **아예 붙이지 않습니다** |
| strict-origin-when-cross-origin | 같은 출처에는 전체 주소를, 다른 출처에는 출처만(경로 제외) 붙입니다. 브라우저의 기본값입니다 |
| referrerpolicy | 요소 하나에 붙이는 같은 이름의 HTML 속성. 여기에 지정한 값이 문서 전체 정책보다 우선합니다 |
| 오류 153 | 유튜브 player 가 Referer 를 받지 못했을 때 재생 화면에 표시하는 번호. 문구는 "동영상 플레이어 구성 오류" |
| ref callback | React 에서 DOM 요소를 받는 방법 2가지 중 하나. 요소가 바뀔 때마다 React 가 다시 호출합니다. 다른 하나인 ref object 는 값만 담고 알림을 주지 않습니다 |

## 오늘 한 것

### 1. 게시판 페이지네이션이 깨지던 문제

**증상** — 공지나 팀 게시판에서 글 1개를 열었다가 목록으로 돌아오면, 표시할 글이 1쪽 분량뿐인데도
페이지 번호가 여러 개 생기고 목록에는 방금 열었던 글 1개만 남았습니다. 사이드바로 공지사항에 다시
들어가면 정상이었습니다.

**원인** — `components/hooks.ts` 의 `useFitCount` 가 목록 상자를 `useEffect` 로 한 번만 붙잡고
있었습니다. 이 훅은 상자 높이를 재서 한 쪽에 표시할 글 개수를 정합니다.

| 시점 | 실제 동작 |
|---|---|
| 목록 진입 | 상자 높이를 재서 개수를 계산합니다 |
| 글 상세 열기 | 상자가 DOM 에서 제거됩니다. ResizeObserver 가 높이 0 을 감지해 개수가 1 이 됩니다 |
| 목록 복귀 | 상자가 **새 요소로** 생성되는데, effect 는 제거된 예전 요소를 붙잡고 있어 다시 측정하지 않습니다 |

개수가 1 로 고정되므로 글이 1개만 보이고 페이지 수는 글 개수만큼 늘어납니다. 사이드바로 다시
들어가면 화면 전체가 새로 생성되어 측정이 정상 동작한 것입니다.

**수정** — ref object 를 ref callback 으로 변경했습니다. React 가 요소가 바뀔 때마다 이전 감시를
정리하고 새 요소로 다시 호출합니다. `routes/Teams.tsx` 의 팀 목록도 같은 훅을 쓰므로 함께
해소됐습니다. 호출하는 쪽에서 고칠 수도 있었지만 훅 하나를 고치는 편이 두 화면을 모두 덮습니다.

**남긴 것** — 이 훅의 자동 검사는 만들지 않았습니다. jsdom 환경과 `ResizeObserver` 대역,
testing-library(미설치)가 필요해 새 의존성 승인이 필요합니다.

### 2. 유튜브 임베드 오류 153

이 건이 오늘 시간을 가장 많이 쓴 곳이고, **틀린 자리를 세 번 팠습니다.** 기록해 둡니다.

**무엇이** — 본문에 넣은 유튜브 영상이 "동영상 플레이어 구성 오류 153" 을 표시했습니다.
**언제** — 배포 환경에서. 개발 서버에서는 나오지 않았습니다.
**어디서** — 재생 화면 안. 코드가 만드는 주소 자체는 정상이었습니다.
**누가** — 개발자님이 배포 화면에서 발견하셨습니다.
**왜** — `deploy/Caddyfile` 이 문서 전체에 `Referrer-Policy "same-origin"` 을 내립니다. 이 값은 다른
출처로 나가는 요청에 Referer 를 붙이지 않고, 유튜브는 Referer 가 없으면 153 을 표시합니다.
**어떻게** — 유튜브 iframe 에만 `referrerpolicy="strict-origin-when-cross-origin"` 을 붙였습니다.

**틀린 자리 3번**

| # | 의심한 것 | 확인 방법 | 결과 |
|---|---|---|---|
| 1 | 주소에 붙는 `origin` 매개변수 | localhost 에서 iframe 으로 직접 열기 | 정상 재생. 원인 아님 |
| 2 | 편집기가 만드는 `src` 가 다름 | 로그인 후 작성 폼에 직접 입력 | 편집기·저장·재생 모두 정상. 원인 아님 |
| 3 | 그 영상만의 임베드 제한 | 개발자님이 Referrer Policy 를 지목 | 지목이 맞았습니다 |

**재현 방법** — 개발 서버에서도 `<meta name="referrer" content="same-origin">` 을 넣으면 배포와 같은
조건이 됩니다. 이 방법으로 153 을 재현하고, `referrerpolicy` 를 붙인 iframe 은 정상 재생되는 것을
나란히 확인했습니다. 이 확인이 없었으면 또 추측으로 고쳤을 것입니다.

**결정 — Caddyfile 을 고치지 않았습니다.** `Referrer-Policy` 를 브라우저 기본값으로 되돌리면 1줄로
끝나지만, 임베드 하나 때문에 사이트 전체의 보안 설정을 여는 것입니다. 요소에 지정한 정책이 문서
정책보다 우선하므로 유튜브 iframe 하나만 열었습니다. 나가는 값은 출처(`https://banblit.com`)뿐이고
경로는 나가지 않습니다.

**이미 저장된 글** — 주소가 본문 HTML 에 박혀 저장되므로, 편집기만 고치면 과거 글은 그대로
153 입니다. `lib/richText.ts` 의 `sanitizeBody` 가 화면에 넣는 시점에 속성을 붙이도록 해서 과거 글도
함께 해소했습니다. 글을 다시 쓸 필요는 없습니다.

**DOMPurify 함정** — 속성을 붙이는 자리를 `uponSanitizeElement` 로 잡으면 지워집니다. 그 hook 은
속성 검사 **전**에 실행되기 때문입니다. `afterSanitizeAttributes` 로 옮기고 허용 속성 목록에
`referrerpolicy` 를 추가해야 남습니다. 검사를 먼저 쓰지 않았으면 못 찾았을 함정입니다.

**삭제한 것** — 주소의 `origin` 매개변수를 없앴습니다. 153 과 무관했고, 개발 환경에서 쓴 글에
`http://localhost:5173` 이 박혀 배포 화면까지 따라가는 문제만 만들고 있었습니다.
