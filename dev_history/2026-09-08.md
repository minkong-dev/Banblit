## 트러블슈팅

### 테스트 292개가 픽스처 단계에서 한꺼번에 터졌습니다

**왜** 테스트 DB 에 옛 `memberships` table이 남아 있었습니다. 픽스처가 `Base.metadata` 를 보고
table 단위로 삭제하는데, 모델에서 없어진 table은 metadata 가 모르므로 유지됩니다. 그 table의 외래키가
`teams` 를 참조해 `teams` 를 다시 만들 수도 없었습니다. **어떻게** 스키마를 통째로 비우도록
변경했습니다(`DROP SCHEMA public CASCADE`). `alembic_version` 도 함께 제거되어 별도로 삭제할 필요가
없어졌습니다.

### 정규식으로 import 줄을 수정하다 파일 4개를 손상시켰습니다

**왜** 2줄 이상에 걸친 `from ... import (...)` 를 한 번에 수정하려고 정규식을 사용했는데,
줄바꿈을 넘어 뒤따르는 주석과 코드까지 포함시켰습니다. **어떻게** `git show HEAD:` 로 원본
import 줄을 추출해 손으로 복구했습니다. **다음부터** 2줄 이상 import 는 정규식으로 수정하지 않습니다.

### 화면 타입 검사가 0개인데 실제로는 손상되어 있었습니다

**왜** 화면이 서버 응답 타입을 `contract.ts` 에 따로 정의하고 있어서, 서버가 변경되어도
타입 검사는 통과합니다. 손상이 나타나는 것은 실행할 때입니다. **어떻게** 변경된 이름(`positions`,
`memberships`, `member_count`, `join_policy`)을 직접 검토해 찾았습니다. **남는 것** 이
구조는 그대로입니다. 서버와 화면의 타입을 연결하는 방식이 없습니다.

## 트러블슈팅 (리팩토링)

# 추가한 기능 — 예약 취소와 불가능 시간 삭제

서버에는 `DELETE /reservations/{id}` 와 `DELETE /members/{id}/unavailable/{time_id}` 가
있었는데 화면에 그 endpoint를 호출하는 자리가 없었습니다. 게다가 날짜 모달이 "예약한 뒤에도 취소하거나
시간을 변경할 수 있어요" 라고 적어두고 있었습니다. 할 수 없는 기능을 가능하다고 안내하고 있었습니다.

## 예약은 칸마다 번호가 다릅니다

서버는 예약을 1시간 단위 행으로 저장합니다. **3시간을 연속으로 예약하면 행이 3개, 번호도 3개**입니다.
그대로 두면 타임라인에 막대가 3개로 나오고, 취소도 3번 눌러야 합니다. 그래서 화면이 먼저
연결합니다 — `lib/slots.ts` 의 `mergeReservations` 가 합주실·팀·예약한 사람이 같고 시각이 맞닿은
칸을 한 건으로 묶고, 그 건의 번호를 전부 가지고 있습니다. 취소는 그 번호를 차례로 삭제합니다.

**팀은 이름이 아니라 번호로 구분했습니다.** 이름으로 구분하면 같은 이름의 팀 2개가 연속으로 예약했을 때
한 건으로 통합되어, 다른 팀의 번호가 내 취소 목록에 섞입니다. 사람을 번호로 구분하는 것과 같은 이유입니다.

## 지우는 자리는 타임라인이 아니라 그 아래 목록입니다

막대 높이가 칸수 × 17px 이라 1시간짜리 예약은 **14px** 입니다. 그 막대에는 클릭할 자리가 없습니다.
그리고 취소는 되돌릴 수 없는 동작이라 14px 조각에 추가할 것이 아닙니다. 이 모달에 이미 있는
"이날 나오는 사람" 줄 형식을 그대로 사용해서 타임라인 아래에 **"내가 설정한 것"** 목록을 두고,
줄마다 삭제 아이콘을 추가했습니다. 새로운 UI 요소를 만들지 않았습니다.

**내 예약인지는 `removeIds` 가 포함되었는지로 구분합니다.** 예전에는 "내 팀의 예약인가"로 구분했는데,
개인 이름으로 예약한 예약은 팀이 없어서 내 일정 탭에 아예 나타나지 않았습니다. 서버가 제공한 예약자 번호와
내 번호를 비교하는 쪽이 정확하고, 다른 팀의 예약에는 애초에 번호가 포함되지 않습니다.

**버튼·물음·알림이 같은 말을 사용합니다.** 예약은 "취소", 불가능 시간은 "삭제"입니다.
`askDelete` 만 있던 자리에 `askCancel` 을 추가한 것은 그래서입니다.

## 시간 변경은 넣지 않았습니다

`PATCH /reservations/{id}` 는 **칸 하나만** 변경합니다. 3시간 예약을 변경하려면 화면이
취소 후 다시 예약을 해야 하는데, 그 사이에 다른 사람이 그 자리를 예약하면 **예약이 그냥 사라집니다.**
서버에 예약 한 건을 통째로 변경하는 원자적 기능이 생기기 전에는 구현하지 않습니다.
대신 화면 문구를 현재 가능한 것으로 수정했습니다. "예약한 뒤에는 내 일정에서 취소할 수 있어요".

# 배포 준비 — reverse proxy·백업·요청 제한

배포해서 사용자에게 넘기기로 정했습니다. 그 전에 남은 3가지를 만들었습니다.

## reverse proxy(Caddy)를 구성했습니다

**reverse proxy(서버 앞에서 요청을 먼저 받아 전달하는 서버)가 없으면 로그인이 성립하지 않습니다.** 배포 설정이 cookie에 `Secure` 를 붙이는데,
브라우저는 그 cookie를 http 연결에서 아예 저장하지 않습니다. 화면도 서버도 오류를 내지 않고
로그인만 안 되는, 원인을 찾기 어려운 종류입니다.

`deploy/Caddyfile` 이 인증서를 스스로 받고 갱신하며 http 를 https 로 변환합니다. `web` 은
호스트 포트를 `127.0.0.1` 로만 바인딩해 외부에서 직접 접근하지 못하게 했습니다. 들어오는 경로는 1개입니다.

**주소가 먼저입니다.** 발급하는 쪽이 그 주소로 확인하러 오므로, DNS 를 설정하고 전파를 확인한
뒤에 실행해야 합니다. 실패를 반복하면 한동안 거절됩니다.

## 백업을 붙였습니다

`deploy/backup.sh` 가 6시간마다 데이터베이스와 첨부파일을 각각 생성합니다. 14일치를 유지합니다.

**생성한 파일을 volume이 아니라 host 폴더에 둡니다.** volume이 사라지는 것이 백업이 막아야 할
바로 그 상황이라, 같은 곳에 두면 함께 없어집니다.

**작성 중인 파일을 남기지 않습니다.** `.part` 로 작성하고 완료되면 이름을 변경합니다. 오래된 것을
삭제하는 것은 생성에 성공한 후에만 합니다. 실패한 날에 삭제하면 정상적인 백업이 하나도 남지 않습니다.

## 요청 제한을 넣었습니다

`api/rate_limit.py`. 로그인·가입·아이디 찾기·재설정 요청·재설정 확인 5곳에 적용했습니다.

- **남은 시도 횟수를 알려주지 않습니다.** 상한을 알면 그 아래로 맞춰 계속 시도합니다.
- **차단된 요청은 세지 않습니다.** 세면 계속 시도하는 동안 창이 밀려 영영 해제되지 않습니다.
- **누가 보냈는지는 reverse proxy가 본 상대로 구분합니다.** 보낸 쪽이 스스로 적은 값을 믿으면 값을
  바꿔 가며 상한을 무한히 피할 수 있습니다. reverse proxy를 하나 더 두면 이 판정을 함께 수정해야 합니다.
- 메일이 나가는 2곳은 상한을 더 낮게 설정했습니다. 남의 주소로 메일을 보내는 데 악용될 수 있습니다.

**세는 자리는 서버 한 대의 메모리 내에 있습니다.** 2대 이상으로 늘리면 대마다 따로 세므로 실제 상한이
대수만큼 커집니다. 현재는 한 대이므로 그대로 유지했습니다.

## 트러블슈팅

- **요청 제한을 적용하자 테스트 195개가 실패했습니다.** 테스트가 한 프로세스에서 요청을 연달아 보내는데
  카운트가 테스트 사이에 남아 로그인 테스트부터 429 오류가 발생했습니다. `conftest.py` 에 테스트마다 카운트를 초기화하는
  fixture를 추가하여 해결했습니다. 상한을 테스트용으로 낮추거나 비활성화하지 않은 것은, 그러면 테스트가 실제 동작과
  다른 것을 검증하게 되기 때문입니다.
- **`COMMAND.md` 11장이 존재하지 않는 파일을 참조하고 있었습니다.** `docker-compose.prod.yml` 입니다. base/override
  로 이동하면서 삭제되었는데 문서만 남아 있었습니다. 배포 절차 5개로 다시 작성했습니다.

## 정한 것

- **개발 환경에서는 reverse proxy·백업을 삭제하지 않고 비활성화합니다.** override에서 profile을 추가했습니다. 삭제하면
  배포용 정의에서도 함께 삭제됩니다.
- **배포 환경에서 마이그레이션은 수동으로 실행합니다.** 개발 환경의 `banblit up` 은 자동으로 실행하지만, 데이터가
  있는 환경에서 자동으로 실행되는 마이그레이션은 되돌릴 수 없습니다.
- **첫 계정이 권한을 전부 받는 것은 그대로 유지합니다**(사용자 결정). 실행한 직후 관리자가 먼저
  가입하는 것으로 방지합니다. 가입 자체를 열어 둔 것도 그대로입니다.

### 미룬 것

- `pydantic-settings` 도입 — 의존성 추가이므로 컨테이너 이미지 재빌드가 필요합니다. 승인을 받은 후 진행합니다.
- E2E 테스트는 깨져 있습니다 — 시드 계정 `e2e@banblit.test` 가 없습니다.
- 메일이 실제로는 발송되지 않습니다 — Gmail 앱 비밀번호를 `.env` 에 추가해야 합니다.
- 달력에 집중 합주기간이 2개 이상이어도 1개만 표시됩니다.
- 소셜 로그인, LLM 도우미 — 아직 시작하지 않았습니다.
- 만료된 session 행·오래된 알림을 삭제하는 기능이 없습니다.
- **예약 시간 변경.** 서버의 `PATCH /reservations/{id}` 는 1시간 칸 하나만 이동합니다. 예약 한 건을
  통째로 이동하는 원자적 endpoint가 필요합니다. 그 전에는 화면에 추가하지 않습니다.
- 화면 컴포넌트에 대한 테스트가 없습니다. `lib/` 순수 계산만 테스트가 있어서, 이번처럼 화면을 변경해도
  테스트는 전부 통과합니다. 위 "눈으로 확인하지 못한 화면" 5줄이 그래서 남습니다.

### 배포 전에 남은 것

reverse proxy·백업·요청 제한은 완성했습니다(위 "배포 준비"). 남은 것은 다음과 같습니다.

1. **서버.** Oracle 가입 대기 중입니다. 서버가 없어 reverse proxy·백업은 아직 실제로 실행해 본 적이 없습니다.
   문법 검사(`caddy validate`)와 개발 구성이 손상되지 않는 것까지만 확인했습니다.
2. **메일.** Gmail 앱 비밀번호를 `.env` 에 추가하면 됩니다. 없으면 비밀번호 찾기 기능이 작동하지 않아
   비밀번호를 잊은 사용자의 복구 경로가 관리자가 데이터베이스를 직접 수정하는 것뿐입니다.
3. **백업을 서버 외부로.** 현재는 서버 내부 폴더까지입니다. 서버 전체를 잃는 경우는 복구할 수 없습니다.
4. **복구를 실제로 해 본 적이 없습니다.** 복구해 본 적 없는 백업은 백업이 아닙니다. 절차는
   `COMMAND.md` 11-5에 적었습니다.

### 배포

도메인 `banblit.com` 을 Cloudflare에서 구매했고 이 프로젝트는 `in-six-strings.banblit.com` 입니다.
Oracle은 가입 대기 중입니다. Caddy로 연결하는 것까지 조사만 완료했습니다.

배포하면 데이터베이스가 서버 한 곳으로 집중됩니다. 그때 2가지가 새로 필요합니다.

- **정기 백업.** 데이터베이스가 `banblit-db-data` Docker 저장 공간 내에만 있습니다. 주기적으로 파일로 생성하여 다른 위치에 둘 수 있는 메커니즘이 필요합니다.
- **데이터베이스 초기화 불가.** 구조를 변경할 때마다 마이그레이션이 기존 데이터를 유지하면서 진행해야 합니다.
