## 고민과 결정의 흐름

### 1. 무엇을 먼저 올릴 것인가
- 현재 만들어진 대부분이 gitignore 대상이라, 공개 가능한 건 README뿐이었다.
- 결정: README만 먼저 push하고, 상세 기획 문서화는 나중으로 미룸. → 이후 이날 안에 `.cluedoc/`로 기획을 문서화했다(로컬 전용).

### 2. LLM을 무엇으로, 비용은
- 고민: 자연어 처리와 충돌 조율에 LLM이 필요한데, API 비용이 부담될까.
- 확인한 사실: 월 20달러 구독(Claude Pro)은 앱에서 쓰는 API와 별개 상품이라 그대로 쓸 수 없다. API는 쓴 만큼 별도 결제.
- 처음엔 "문장 하나 파싱" 수준으로 가볍게 봤으나, 실제 역할이 "배정 실패 시 전체 상황을 읽고 조율안 제시"까지라 무거운 작업임을 확인.
- 결정: Claude API 별도 결제(호출이 잦지 않아 소액), 실제 연동은 추후. 완전 무료(자체 모델)는 정확도·안정성 때문에 보류.

### 3. 자동 배정 알고리즘
- 선택지: (직접 구현: 가볍고 투명하나 실수 위험) vs (OR-Tools: 검증된 도구, 정확·공정하나 무겁고 3.14 설치 우려).
- 결정: OR-Tools(CP-SAT). 이유 — 여러 조건을 한 번에 정확히 맞추고, 공정 분배를 잘하며, 검증된 도구라 신뢰. Python 3.14에서 설치·동작을 먼저 확인한 뒤 채택.

### 4. 3단계 우선순위의 재해석 (기획 변경)
- 원래 기획: ①전원 가능 ②팀 간 슬롯 교환 ③특정 인원 제외.
- 발견: 이 3단계는 "직접 짜다가 막히면 교환"하는 방식을 가정한 순서였다. OR-Tools는 전역으로 한 번에 풀기 때문에 "교환"이 1순위 계산에 이미 흡수된다.
- 결정(사용자 승인): 2순위는 별도 단계로 두지 않음. 결과를 "배정 찾음→확정" / "못 찾음→인원 제외 제안" 두 갈래로 단순화. `.cluedoc` 자동배정·LLM 문서도 이에 맞게 갱신.

### 5. 실행 환경과 배포
- venv를 쓴 이유를 두고 혼선 → 정리: DB는 Docker, 파이썬 코드는 로컬 venv(순수 계산 단계라 빠른 테스트용). venv는 커밋 대상이 아님.
- 결정: 웹 서비스이므로 docker-compose 3종(프론트·백·DB)로 간다. 클라우드 배포가 최종 목적지이나, 올릴 앱이 생긴 뒤 결정(컨테이너 선택이라 이전 부담은 적음).

## 트러블슈팅

### T1. 첫 커밋이 거부됨 — "Author identity unknown"
- 무엇: 커밋 시 신원 미확인으로 거부.
- 원인: 로컬 git config에 키 이름이 `user.emall`(i 누락 오타)로 되어 있어 `user.email`이 비어 있었다. 이름은 있었으나 이메일이 없어 커밋이 막힘.
- 처리: 올바른 키 `user.email`에 같은 값(minkyu010521@gmail.com)을 넣고 오타 키 제거 → 커밋 성공.

### T2. push 403 — 회사 계정으로 인증됨
- 무엇: `git push`가 403(Permission denied to joy-company).
- 원인: 회사 PC의 시스템 자격증명 관리자(GCM)가 github.com에 대해 회사 계정 `joy-company`를 내주는데, 이 계정은 개인 저장소(minkong-dev/Banblit) push 권한이 없었다.
- 처리: 이 저장소 로컬 설정에서 시스템 GCM을 우회해 전용 store 자격증명을 쓰도록 구성. 사용자가 `minkong-dev` + 토큰으로 한 번 인증해 저장.

### T3. 토큰이 대화에 노출됨
- 무엇: 문제 해결 중 개인 액세스 토큰(PAT)을 명령 URL에 직접 넣어 노출됨.
- 처리: 해당 토큰 폐기 권고. 인증은 저장소 전용 store에 저장해 재입력 없이 쓰도록 정리.

### T4. 내가 store 설정을 지워 push가 다시 깨짐
- 무엇: "브라우저 로그인으로 GCM이 minkong-dev를 저장했다"고 오판해 저장소 전용 store 설정을 제거 → 이후 push가 다시 회사 계정(joy-company)으로 인증되어 실패.
- 원인: 실제로 minkong-dev push를 되게 한 건 store 설정이었는데 그것을 지웠다(내 판단 착오).
- 처리: store 설정 복구. push 실패 시 `git credential fill`로 어떤 계정이 나오는지 먼저 확인하는 절차를 메모리에 기록.

### T5. 슬롯 단위 0 → 무한 반복 (테스트가 멈춤)
- 무엇: `unit_minutes=0` 방어 테스트를 돌리자 pytest가 멈춤(hang).
- 원인: `generate_slots`가 단위 0일 때 종료 조건을 못 만나 무한 루프.
- 처리: 백그라운드 프로세스 종료 후 `unit_minutes <= 0`이면 ValueError를 내도록 방어 코드 추가.

### T6. 인원 제외 제안의 허점 (코드 리뷰에서 발견)
- 무엇: 리뷰어가 지적 — 팀에 한 명뿐인데 그 사람을 빼면 팀이 텅 비는데도 "빼면 된다"고 제안.
- 원인: 빈 팀의 "전원 가능"이 공허 참(all([])==True)이 되어, 로스터 없는 팀이 배정 가능한 것으로 처리됨.
- 처리: 제외 시 어느 팀이든 비게 되면 그 제안을 건너뛰도록 가드 추가. 실패 테스트로 재현 후 수정.
