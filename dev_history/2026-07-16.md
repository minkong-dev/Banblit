## 고민과 결정의 흐름

### 1. 무엇을 먼저 올릴 것인가
- 현재 만들어진 대부분이 gitignore 대상이라, 공개 가능한 것은 README뿐이었습니다.
- 결정: README만 먼저 push하고, 상세 기획 문서화는 나중으로 미룹니다. 이를 통해 이날 안에 `.cluedoc/`으로 기획을 문서화했습니다(로컬 전용).

### 2. LLM을 무엇으로, 비용은
- 고민: 자연어 처리와 충돌 조율에 LLM이 필요한데, API 비용이 부담될까요.
- 확인한 사실: 월 20달러 구독(Claude Pro)은 앱에서 쓰는 API와 별개 상품이라 그대로 쓸 수 없습니다. API는 쓴 만큼 별도 결제됩니다.
- 처음에는 문장 하나 파싱 수준으로 가볍게 봤으나, 실제 역할이 배정 실패 시 전체 상황을 읽고 조율안을 제시하는 것까지라 무거운 작업임을 확인했습니다.
- 결정: Claude API 별도 결제(호출이 잦지 않아 소액), 실제 연동은 추후에 진행합니다. 완전 무료(자체 모델)는 정확도·안정성 때문에 보류합니다.

### 3. 자동 배정 알고리즘
- 선택지: (직접 구현: 가볍고 투명하나 실수 위험) vs (OR-Tools: 검증된 도구, 정확·공정하나 무겁고 3.14 설치 우려).
- 결정: OR-Tools(CP-SAT)를 채택합니다. 이유: 여러 조건을 한 번에 정확히 충족하고, 공정 분배를 잘하며, 검증된 도구라 신뢰할 수 있습니다. Python 3.14에서 설치·동작을 먼저 확인한 뒤 채택했습니다.

### 4. 3단계 우선순위의 재해석 (기획 변경)
- 원래 기획: ①전원 가능 ②팀 간 slot(1시간 단위 시간 칸) 교환 ③특정 인원 제외.
- 발견: 이 3단계는 직접 짜다가 실패했을 경우 교환하는 방식을 가정한 순서였습니다. OR-Tools는 전역으로 한 번에 풀기 때문에 교환이 1순위 계산에 이미 흡수됩니다.
- 결정(사용자 승인): 2순위는 별도 단계로 두지 않습니다. 결과를 배정 성공→확정 또는 배정 실패→인원 제외 제안 두 갈래로 단순화합니다. `.cluedoc` 자동배정·LLM 문서도 이에 맞게 갱신했습니다.

### 5. 실행 환경과 배포
- venv를 쓴 이유를 두고 혼선이 있었습니다. 정리: DB는 Docker, 파이썬 코드는 로컬 venv(순수 계산 단계라 빠른 테스트용)에서 실행합니다. venv는 커밋 대상이 아닙니다.
- 결정: 웹 서비스이므로 docker-compose 3종(프론트·백·DB)으로 구성합니다. 클라우드 배포가 최종 목적지이나, 배포할 앱이 생긴 뒤 결정합니다(컨테이너 선택이라 이전 비용은 적습니다).

## 트러블슈팅

### T1. 첫 커밋이 거부됨 — "Author identity unknown"
- 무엇: 커밋 시 신원 미확인으로 거부됩니다.
- 원인: 로컬 git config에 키 이름이 `user.emall`(i 누락 오타)로 되어 있어 `user.email`이 비어 있었습니다. 이름은 있었으나 이메일이 없어 커밋이 실패했습니다.
- 처리: 올바른 키 `user.email`에 같은 값(minkyu010521@gmail.com)을 넣고 오타 키를 제거했습니다. 이를 통해 커밋이 성공했습니다.

### T2. push 403 — 회사 계정으로 인증됨
- 무엇: `git push`가 403(Permission denied to joy-company)으로 실패합니다.
- 원인: 회사 PC의 시스템 자격증명 관리자(GCM)가 github.com에 대해 회사 계정 `joy-company`를 제공하는데, 이 계정은 개인 저장소(minkong-dev/Banblit) push 권한이 없었습니다.
- 처리: 이 저장소 로컬 설정에서 시스템 GCM을 우회해 전용 store 자격증명을 사용하도록 구성했습니다. 사용자가 `minkong-dev` + 토큰으로 한 번 인증해 저장했습니다.

### T3. 토큰이 대화에 노출됨
- 무엇: 문제 해결 중 개인 액세스 토큰(PAT)을 명령 URL에 직접 넣어 노출되었습니다.
- 처리: 해당 토큰을 폐기하도록 권고했습니다. 인증은 저장소 전용 store에 저장해 재입력 없이 사용하도록 정리했습니다.

### T4. 내가 store 설정을 지워 push가 다시 깨짐
- 무엇: 브라우저 로그인으로 GCM이 minkong-dev를 저장했다고 잘못 판단해 저장소 전용 store 설정을 제거했습니다. 이후 push가 다시 회사 계정(joy-company)으로 인증되어 실패했습니다.
- 원인: 실제로 minkong-dev push를 성공하게 한 것은 store 설정이었는데 그것을 삭제했습니다(판단 착오).
- 처리: store 설정을 복구했습니다. push 실패 시 `git credential fill`로 어떤 계정이 제공되는지 먼저 확인하는 절차를 메모리에 기록했습니다.

### T5. 슬롯 단위 0 → 무한 반복 (테스트가 멈춤)
- 무엇: `unit_minutes=0` 방어 테스트를 실행하자 pytest가 정지합니다.
- 원인: `generate_slots`가 단위 0일 때 종료 조건을 만나지 못해 무한 루프가 발생합니다.
- 처리: 백그라운드 프로세스를 종료한 후 `unit_minutes <= 0`이면 ValueError를 발생시키도록 방어 코드를 추가했습니다.

### T6. 인원 제외 제안의 허점 (코드 리뷰에서 발견)
- 무엇: 리뷰어가 지적했습니다. 팀에 한 명뿐인데 그 사람을 제외하면 팀이 비어 있는데도 제외하면 된다고 제안합니다.
- 원인: 빈 팀의 전원 가능 판단이 공허 참(all([])==True)이 되어, 로스터가 없는 팀이 배정 가능한 것으로 처리됩니다.
- 처리: 제외했을 때 어느 팀이든 비게 되면 그 제안을 건너뛰도록 가드를 추가했습니다. 실패 테스트로 재현한 후 수정했습니다.
