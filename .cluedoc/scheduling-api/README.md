## Abstract

서버가 화면에 제공하는 endpoint(API의 요청 주소 단위) 전체가 따르는 **공통 규칙** 3가지를 다룹니다. 호출 권한 검증, 잘못된 요청에 대한 응답 형식, 서버 상태 확인 endpoint입니다. 개별 endpoint가 무엇을 하는지는 각 기능 문서가 담당하고, 배정을 계산하고 저장하는 endpoint는 [기간 자동 배정](./period-assignment/README.md)이 담당합니다.

처음에는 팀·합주실을 **이름으로 직접 보내면 저장하지 않고 계산만 하는** `POST /assign`이 이 문서의 주제였습니다. 저장소가 생기고 화면이 기간 번호 1개로 호출하는 endpoint만 쓰게 되면서, `POST /assign`과 이름↔번호 변환 계층은 2026-09-08에 제거했습니다(사용자 결정). 로그인만 하면 어떤 이름으로든 22초가 걸리는 계산을 실행할 수 있던 endpoint도 함께 제거했습니다.

## Introduction

endpoint는 10개 이상이고 각각 하는 일이 다르지만, 3가지는 모든 endpoint에서 같아야 합니다. 요청한 사용자를 검증하는 방식이 endpoint마다 다르면 endpoint 1개의 검증 누락이 전체의 취약점이 되고, 오류 응답의 형식이 다르면 화면이 형식마다 따로 처리해야 하고, 상태 확인이 실제 상태를 반환하지 않으면 중지된 서버가 실행 중이라고 보고됩니다. 이 문서는 그 3가지를 적습니다.

## Description

### 호출 권한은 1곳에서 검증합니다

endpoint마다 요구 조건만 선언합니다. "로그인한 사용자" 또는 "이 권한 항목이 켜진 사용자"입니다. 실제로 cookie를 읽어 사용자를 찾고 그 사용자의 permission set(권한 집합)을 합쳐 판정하는 코드는 `auth_dependency.py` 1곳뿐이고, 모든 endpoint가 그 1곳을 거칩니다.

| 요청 | 응답 |
| --- | --- |
| cookie가 없거나 session이 만료됨 | 401 · 로그인이 필요합니다 |
| 로그인했지만 그 endpoint가 요구하는 권한 항목이 꺼져 있음 | 403 · 권한이 없습니다 |
| 통과 | endpoint 본문 |

401과 403을 구분하는 이유는 화면의 동작이 다르기 때문입니다. 401이면 로그인 화면으로 이동하고, 403이면 현재 화면에 머문 채 안내만 표시합니다. 2개를 합치면 권한이 없는 사용자를 로그인 화면으로 보내, 다시 로그인하면 되는 것으로 오인하게 합니다.

상태 확인(`/health`)만 이 검증을 거치지 않습니다. 서버가 실행 중인지 묻는 호출자는 사용자가 아닙니다.

### 잘못된 요청에는 문장 1개로 응답합니다

형식이 잘못되었든(필수 항목 누락, 개수 상한 초과) 규칙에 위반되었든(이름 중복, 정각이 아닌 시각, 집중 합주기간에 예약) 오류 응답의 형식은 1가지입니다. `detail`에 사용자가 읽을 **문장 1개**를 담습니다. 화면은 그 문장을 그대로 표시하면 되고, 오류 종류마다 다른 형식을 처리할 필요가 없습니다.

형식 오류는 FastAPI가 항목별 목록으로 반환하는데, 그 목록을 문장 1개로 변환하는 처리가 앱에 1개 있습니다. 규칙 위반은 서비스 함수가 발생시킨 문장을 422에 그대로 담아 반환합니다.

"요청은 올바르지만 결과가 없다"는 오류가 아닙니다. 배정 계산이 조건을 충족하는 시간표를 찾지 못하면 200에 조율안을 담아 반환합니다. 그 차이는 [기간 자동 배정](./period-assignment/README.md)에 있습니다.

### 상태 확인은 실제 상태를 반환합니다

상태 확인 endpoint는 "실행 중"이라는 고정된 응답을 반환하지 않습니다. 호출할 때마다 저장소에 실제로 접속하고 적용된 마이그레이션 번호까지 읽어서 그 결과를 그대로 담아 반환합니다. 접속은 되는데 마이그레이션이 아직 적용되지 않았다면 기동 준비가 끝나지 않은 상태이므로 정상이 아니라고 응답합니다. 고정된 응답을 반환하는 상태 확인은 장애를 감지하지 못하고, 저장소가 중지된 서버에도 요청이 계속 전달됩니다.

저장소에 접속하지 못하면 "지금은 받을 수 없습니다"라고 응답합니다. 5종류의 실패를 화면이 구별해야 하기 때문입니다.

| 상황 | 응답 | 화면이 해야 할 일 |
| --- | --- | --- |
| 요청이 잘못됨 | 422 | 무엇이 잘못됐는지 사용자에게 표시합니다 |
| 로그인하지 않음 | 401 | 로그인 화면으로 이동합니다 |
| 로그인했지만 권한이 없음 | 403 | 권한이 없다고 표시합니다. 로그인 화면으로 이동하지 않습니다 |
| 저장소에 접속하지 못함 | 503 | 실패를 표시하고 **재시도 버튼**을 제공합니다 |
| 그 밖의 서버 오류 | 500 | 사용자가 할 수 있는 조치가 없습니다 |

503을 받은 화면은 자동으로 다시 보내지 않습니다. 자동 재시도를 넣으면 저장소가 이미 부하를 받고 있는 상황에서 요청 수가 증가하기 때문에, 실패를 표시하고 재시도 버튼을 제공해 다시 보낼지를 사용자가 결정하게 했습니다.

대기 시간에도 상한이 있습니다. 저장소 접속을 여는 대기 시간과 이미 열린 접속을 받는 대기 시간 모두 상한을 정했는데, 상한이 없으면 저장소가 응답하지 않을 때 요청이 무한정 대기해 그 대기 자체가 장애가 되기 때문입니다. 상한 값은 환경변수로 변경할 수 있습니다.

접속 실패의 실제 사유에는 접속 주소나 계정 이름 같은 내부 정보가 들어 있습니다. 화면에는 사용자가 읽을 문장 1개만 보내고, 원인 분석용 상세 내용은 로그에 기록합니다.

### 컨테이너에서 서버를 실행합니다

개발할 때는 소스 코드를 마운트한 서버를 컨테이너로 실행하여, 코드를 수정하면 서버가 자동으로 다시 시작합니다. 배포용 이미지는 실행 명령 자체가 이 서버를 시작하는 명령이므로 이미지를 실행하면 바로 서버가 요청을 받을 수 있습니다. 배포용 이미지에는 테스트 도구를 포함하지 않고 실행에 필요한 패키지만 남깁니다.

이 서버는 화면 파일을 제공하지 않습니다. 브라우저는 화면을 받은 출처와 다른 출처로 보내는 요청을 차단하는데(CORS 정책), 사용자가 실제로 쓰는 앱은 화면 개발 서버에서 실행되고 그 서버가 API 경로만 이 서버로 전달하므로 이 문제가 발생하지 않습니다. 한동안 확정된 설계를 담은 정적 화면을 개발할 때만 함께 제공했지만, 앱이 그 설계를 전부 구현한 뒤 정적 화면과 함께 제공 경로도 삭제했습니다.

### 트러블슈팅

**문제 1 — 한글이 든 요청이 서버에서 깨짐**

- **언제**: 컨테이너로 띄운 서버에 배정 요청을 직접 보내 실제로 동작하는지 확인하던 중
- **어디서**: Windows PC의 Git Bash 셸에서 `curl` 명령을 실행하는 과정
- **무엇이 벌어졌나**: 합주실 이름 "1번방"처럼 한글이 포함된 JSON 요청 본문을 작은따옴표로 감싼 인라인 인자(`curl -d '...'`)로 넘겼더니, 서버가 요청 자체를 읽지 못했다는 오류를 반환했습니다
- **왜 그런가**: Git Bash가 작은따옴표로 감싼 인라인 인자를 셸에서 처리하는 과정에서 그 안의 한글 문자를 UTF-8 그대로 전달하지 못했고, 그 결과 서버에 도착한 시점에는 이미 올바른 JSON이 아니었습니다. 서버나 계산 로직의 결함이 아니라 셸이 인라인 인자를 처리하는 방식에서 발생한 문제였습니다
- **어떻게 해결했나**: 요청 본문을 UTF-8로 인코딩된 파일로 먼저 저장한 뒤 `curl`의 `--data-binary @파일이름` 옵션으로 그 파일을 그대로 전송했습니다. 파일 내용은 셸의 인라인 인자 처리 경로를 거치지 않으므로 한글이 깨지지 않습니다
- **남는 영향**: 이후로도 한글이 포함된 요청을 Git Bash에서 직접 검증할 때는 인라인 인자 대신 파일 전달 방식을 사용합니다

**문제 2 — 서버를 띄우려는 포트를 다른 프로젝트가 이미 사용하고 있었음**

- **언제**: 개발용 서버를 컨테이너로 띄우려던 시점
- **어디서**: 같은 PC에서 이 저장소와 무관한 다른 프로젝트("infrastructure"라는 이름의 별도 서비스 묶음)가 이미 실행 중이었습니다
- **무엇이 벌어졌나**: 이 서버가 사용하려는 포트를 그 다른 프로젝트의 컨테이너가 먼저 차지하고 있어, 포트를 여는 시도가 "이미 사용하고 있다"는 오류로 실패했습니다
- **왜 바로 중지하지 않았나**: 이 저장소의 규칙상, 이 작업과 무관하게 이미 동작 중인 프로그램을 중지하는 것처럼 되돌리기 어려운 작업을 하기 전에는 반드시 먼저 사용자에게 이유를 설명하고 승인을 받아야 합니다. 그 다른 프로젝트가 중지되었을 때 어떤 영향이 있을지 이 작업만으로는 알 수 없었기 때문에 임의로 중지하지 않고 먼저 상황을 보고했습니다
- **어떻게 해결했나**: 사용자에게 상황을 설명하고 승인을 받은 뒤 그 다른 프로젝트의 서비스 묶음을 중지하여 포트를 비웠고, 이후 이 저장소의 서버가 그 포트를 정상적으로 사용할 수 있었습니다
- **남는 영향**: 이 문제는 이 저장소 코드의 결함이 아니라 개발 환경에서 포트가 겹칠 때 발생하는 상황입니다. 같은 포트를 사용하는 다른 프로그램이 실행 중이면 다시 발생할 수 있고, 그때도 같은 절차(원인 확인 → 사용자 승인 → 정리)를 따릅니다

## Conclusion

호출 권한 검증 방식, 오류 응답 형식, 상태 확인 endpoint. 이 3가지 위에 각 기능의 endpoint가 구현됩니다. 배정을 계산하고 저장하는 endpoint는 [기간 자동 배정](./period-assignment/README.md)으로 이어집니다.
