## Abstract

기간 자동 배정은 이미 저장된 기간·팀·소속·합주실·불가능시간 데이터를 읽어 그 기간 전체의 시간표를 계산하고 저장까지 수행하는 endpoint(API의 요청 주소 단위)입니다. 호출하는 쪽은 배정할 팀과 합주실의 번호만 보내면 되고, 나머지(배정 대상 날짜, 팀당 slot 개수, 화면에 표시할 이름)는 저장된 데이터로부터 이 계층이 채웁니다. 계산이 성공하면 즉시 현행 시간표로 저장하고, 실패하면 오류가 아니라 조율안을 담아 반환합니다. 배정·조회·되돌리기 3개 endpoint가 이 흐름을 구성합니다.

## Introduction

이전의 [스케줄링 API](../README.md)는 요청 1번에 팀·멤버·합주실 정보를 전부 담아 보내야 계산할 수 있었습니다. 실제 운영에서는 그 정보가 이미 데이터베이스에 있으므로 매번 다시 보내는 일은 번거롭고 입력 실수가 발생할 수 있습니다. 이 계층은 그 정보를 데이터베이스에서 직접 읽어, 기간 1개를 지정하는 것만으로 계산을 실행합니다.

이 계층이 해결해야 할 문제는 3가지였습니다. 첫째, 계산 엔진은 "기간"이라는 개념을 모르고 하루치 운영시간과 팀 목록만 받으므로 기간의 시작일부터 종료일까지의 모든 날짜를 계산 엔진이 받는 형태로 펼쳐야 합니다. 둘째, 계산 엔진은 번호만 받고 이름은 받지 않으므로 저장소의 번호를 그대로 넘기고 결과가 나오면 화면에 표시할 이름을 그때 붙여야 합니다. 셋째, 계산이 성공한 시간표를 저장하지 않으면 다시 조회할 방법이 없으므로 성공한 결과는 즉시 저장해야 하고, 그 저장은 [배정 이력과 롤백](../../database-layer/schedule-versioning/README.md)이 이미 정해 둔 백업·롤백 규칙을 그대로 따릅니다.

## Description

### endpoint는 5개입니다

| endpoint | 무엇을 하는가 | 부를 수 있는 사람 | 정상 응답 |
| --- | --- | --- | --- |
| 배정 | 팀 번호 목록과 합주실 번호 목록을 받아, 그 기간 전체의 시간표를 계산하고 성공하면 저장합니다 | 배정 계산 항목이 켜진 사용자 | 배정 결과(성공 시) 또는 조율안(실패 시) |
| 조회 | 그 기간에 현재 저장된 시간표를 실제 팀 이름·합주실 이름과 함께 반환합니다 | 로그인한 사용자 전체 | 저장된 배정 행 목록(없으면 빈 목록) |
| 되돌리기 | 그 기간의 가장 최근 백업으로 현행 시간표를 되돌립니다 | 되돌리기 항목이 켜진 사용자 | 되돌렸는지 여부 |
| 배정기록 목록 | 그 기간의 백업 배정기록을 저장 시각과 slot 수와 함께 최신순으로 반환합니다 | 되돌리기 항목이 켜진 사용자 | 배정기록 목록(없으면 빈 목록) |
| 배정기록 시간표 | 배정기록 1개의 저장 시각을 받아, 그 배정기록의 시간표를 실제 이름과 함께 반환합니다 | 되돌리기 항목이 켜진 사용자 | 그 배정기록의 배정 행 목록 |

시간표를 변경하는 2개 endpoint(배정, 되돌리기)는 각각의 권한 항목이 켜진 사용자에게만 허용하고, 확정된 시간표를 조회하는 endpoint는 로그인한 사용자 전체에게 허용합니다. 2개 endpoint가 서로 다른 권한 항목을 요구하므로 계산은 실행하지 못하고 되돌리기만 담당하는 사용자를 둘 수 있습니다. 권한 항목이 무엇이고 어떻게 켜고 끄는지는 [계정과 역할](../../accounts-and-roles/README.md)이 정본이고, 계산 완료 여부를 polling(주기적으로 서버에 같은 요청을 다시 보내 변경을 확인하는 방식)하는 endpoint까지 포함한 전체 규칙과 401·403을 구분하는 이유는 [스케줄링 API](../README.md)에 있습니다.

5개 endpoint 모두 기간 번호 1개를 기준으로 동작합니다. 배정 endpoint는 집중 합주기간에서만 실행할 수 있고, 그 밖의 기간에는 자동 배정 자체가 적용되지 않으므로 계산 전에 거부합니다.

### 기간 전체를 날짜와 합주실로 펼칩니다

배정 대상 날짜는 기간의 "매일" 옵션에 따라 다릅니다(사용자 결정 2026-09-11). 옵션이 꺼진 기간은 시작일부터 종료일까지 양 끝을 포함한 모든 날입니다. 옵션이 켜진 기간은 종료일이 없으므로, 계산을 실행한 날(저장 시각의 날짜) 하루만 배정 대상입니다. 남는 slot 을 조회할 때도 같은 규칙을 적용하며, 이때의 "실행한 날" 은 조회한 날입니다. 옵션이 켜진 기간에 저장된 종료일은 참조하지 않습니다. 옵션이 켜진 기간이 예약을 어떻게 거절하는지는 [합주실과 기간](../../practice-room-and-periods/README.md)에서 다룹니다.

날짜 목록이 정해지면 요청에 담긴 합주실 1개마다 그 날짜 수만큼 늘립니다. 계산 엔진은 합주실 1개에 연속한 운영시간 1개만 받으므로, 같은 합주실이라도 날짜가 다르면 서로 다른 합주실로 계산에 넘겨야 하기 때문입니다. 예를 들어 합주실이 2개, 기간이 2주(14일)면 계산 엔진에는 28개의 합주실이 들어갑니다. 이렇게 늘어난 합주실 각각의 운영시간을 1시간 slot으로 나눈 결과가 그 기간의 전체 slot입니다.

팀당 slot 개수는 전체 slot 수를 팀 수로 나눠 자동으로 정하고, 나머지는 배정하지 않는 남는 slot이 됩니다. 팀 수가 전체 slot 수보다 많아 팀마다 slot 1개도 배정할 수 없는 경우에는 계산을 시작하지 않고 거부하고, 배정할 팀이 0개인 요청도 같은 방식으로 거부합니다.

### 저장소의 번호를 그대로 계산에 넘깁니다

계산 엔진은 팀·합주실·사람을 번호로만 구분합니다. 이 계층은 저장소에서 번호를 읽으므로 별도의 식별자를 생성할 필요가 없습니다.

```
저장소                        계산                       응답
합주실 7번 "1번방"     ──►    합주실 7 × 날짜마다   ──►   7번 + "1번방"
사람 12번 "김민수"     ──►    사람 12              ──►   12번 + "김민수"
사람 34번 "김민수"     ──►    사람 34              ──►   34번 + "김민수"
```

동명이인은 저장소에서 이미 다른 번호이므로 계산에서도 다른 사람입니다. 같은 사람이 2개 이상 팀에 속해 있으면 번호가 1개뿐이라, 계산은 그 사람이 같은 시간에 2개 팀에 동시에 배정될 수 없다는 조건을 적용합니다.

같은 합주실이 날짜마다 다시 사용되어도 번호를 나눌 필요가 없습니다. slot 1개는 합주실 번호와 시작 시각 2개 값으로 식별하므로, 같은 합주실이라도 날짜가 다르면 slot도 다릅니다. 이름은 계산에 들어가지 않고, 결과를 반환할 때 저장소에서 읽어 둔 이름을 번호에 붙여 반환합니다.

멤버가 등록한 불가능시간 중 매주 반복으로 표시된 불가능시간은 그 기간 안에서 실제로 겹치는 구간으로 전개하여 계산에 넘깁니다. 반복은 7일 간격으로 되풀이하되 반복 종료일이 정해져 있으면 그 날짜까지만 만들고, 기간과 겹치지 않는 구간은 만들지 않습니다. 계산에 넘겨도 결과에 영향이 없는 값을 넘길 이유가 없기 때문입니다.

### 성공하면 즉시 저장하고, 실패하면 조율안을 반환합니다

계산이 조건을 충족하는 시간표를 찾으면 즉시 현행 시간표로 저장합니다. 저장은 [배정 이력과 롤백](../../database-layer/schedule-versioning/README.md)의 규칙을 그대로 따라서, 그 기간에 이미 저장된 시간표가 있으면 저장시각을 기록하여 백업으로 이동하고 백업은 최근 2개 배정기록만 남깁니다. 계산이 조건을 충족하는 시간표를 찾지 못하는 경우는 오류가 아니므로, 아무것도 저장하지 않고 "누구를 제외하면 되는지" 조율안을 담아 정상 응답으로 반환합니다.

되돌리기는 새로운 규칙을 만들지 않고, 그 기간의 가장 최근 백업을 현행 시간표로 되돌리는 저장 규칙을 그대로 호출할 뿐입니다. 되돌릴 백업이 없으면 아무것도 변경하지 않고 "되돌린 배정기록이 없다"고만 응답합니다.

### 백업 배정기록을 선택하여 그 시간표를 조회합니다 (2026-09-08)

되돌리기는 언제나 **바로 직전 배정기록**으로만 되돌립니다. 되돌릴 배정기록을 선택하는 기능은 없습니다. 그래서 되돌리기 전에 직전 배정기록의 시간표를 조회할 수 있어야 합니다. 조회할 수 없으면 되돌린 뒤에야 어떤 시간표로 돌아왔는지 알게 됩니다.

배정기록을 식별하는 값은 **저장 시각**입니다. 백업에는 별도의 배정기록 번호가 없고, 같은 시점에 백업된 slot들이 같은 저장 시각을 공유합니다. 그 시각으로 조회하면 그 시점의 시간표 1벌이 됩니다.

```
배정기록 목록          배정기록 시간표
─────────────      ─────────────────────────
9월 8일 21:00  ──▶  1번방 19:00 새벽 네시
 (칸 12개)          1번방 20:00 파랑주의보
                    2번방 19:00 오프비트  …
9월 7일 21:00
 (칸 10개)
```

**slot이 0개인 배정기록은 존재하지 않는 배정기록입니다.** 빈 시간표는 저장되지 않으므로, 그 저장 시각으로 조회 결과가 0개이면 "빈 배정기록"이 아니라 "존재하지 않는 배정기록"입니다. 빈 목록을 반환하면 화면이 "그 배정기록에는 합주가 없었다"로 표시하므로, 존재하지 않는 배정기록 요청은 거절합니다.

2개 endpoint 모두 **되돌리기와 같은 권한 항목**으로 검증합니다. 배정기록 시간표는 배정기록 목록에서 이어지는 화면이므로, 2개 endpoint의 권한이 다르면 목록만 표시되고 선택해도 열리지 않는 상태가 됩니다.

### 시간표를 변경한 뒤에는 알림을 생성합니다 (2026-09-07)

이 계층에서 시간표가 변경되는 경우는 3가지입니다. 배정이 성공해 저장될 때, 조율안 1개를 선택해 확정 저장할 때, 되돌리기가 이전 배정기록을 복원했을 때입니다. 3가지 모두에서 그 기간에 slot을 받은 팀의 멤버에게 알림 1개가 생성됩니다.

```
배정 계산  ─┐
조율안 확정 ─┼─▶ 저장이 실제로 됐다  ─▶  slot 을 받은 팀의 사람에게 알림
되돌리기   ─┘        │
                     └─ 안 됐다 (조율안만 나옴 · 되돌릴 배정기록 없음) ─▶ 아무것도 안 남긴다
```

배정과 조율안 확정은 같은 endpoint를 사용합니다. 조율안 확정은 "제외 대상을 뺀 채로 같은 계산을 다시 실행하는 것"이라 저장 경로가 1개로 유지되고, 그래서 알림을 생성하는 코드도 1곳뿐입니다. 되돌리기는 계산을 거치지 않는 별개의 경로이므로 되돌리기 endpoint에서 따로 생성합니다.

알림 대상, 저장이 완료된 때만 생성하는 이유, 자동 실행 계산과 순서가 어떻게 다른지는 [자동 배정](../../auto-assignment/README.md)이 정본입니다. 이 계층이 추가하는 규칙은 "사용자가 배정 화면에서 변경한 시간표도 자동 계산으로 변경된 시간표와 같게 알린다" 1가지입니다.

### 거부하는 경우

배정 계산을 시작하기 전에 다음 입력은 거부합니다.

| 입력 | 거부 사유 |
| --- | --- |
| 그런 기간·팀·합주실 번호가 없음 | 존재하지 않는 대상을 배정할 수 없습니다 |
| 집중 합주기간이 아닌 기간에 배정을 요청함 | 자동 배정은 집중 합주기간에서만 실행됩니다 |
| 팀 번호 목록에 같은 번호가 2번 들어옴 | 오류 메시지 없이 1개로 합쳐지면 실제로 몇 팀이 배정 대상인지 알 수 없게 됩니다 |
| 합주실 번호 목록에 같은 번호가 2번 들어옴 | 위와 같은 이유 |
| 팀마다 slot 1개도 배정할 수 없을 만큼 slot이 부족함 | 계산 자체가 의미 없는 요청입니다 |
| 소속 멤버가 없는 팀이 포함됨 | 멤버가 0명인 팀에 slot을 배정할 수 없습니다 |

계산이 끝난 뒤 저장 시점에 발생하는 거부도 1가지 있습니다. 다른 기간이 이미 같은 합주실의 같은 시각을 현행 시간표로 사용하고 있으면 저장이 거부됩니다. 집중 합주기간끼리는 날짜가 겹칠 수 없으므로(migration `b5e1d9a37c42`), 배정을 저장한 기간의 날짜를 변경해 옛 날짜에 배정이 남고 그 날짜에 새 기간을 만들어 같은 합주실을 사용하면 발생합니다. 이 경우 기간을 겹치지 않게 하거나 합주실을 나누라는 안내와 함께 거부하고, 먼저 저장되어 있던 다른 기간의 현행 시간표는 그대로 유지되며 이번 요청만 실패로 처리됩니다.

### 성능을 함께 측정했습니다

2주(14일) × 합주실 2개 × 팀 4개 규모의 배정 계산이 실제로 끝까지 도는지와 얼마나 걸리는지를 같은 테스트로 함께 확인했습니다. 이 규모는 하루 4시간씩 운영하는 합주실 2개를 2주 동안 4개 팀이 나눠 쓰는 상황에 해당합니다.

측정은 `pytest`의 `--durations` 옵션으로 했습니다. 이 옵션은 테스트가 끝난 뒤 실행 시간이 긴 테스트부터 순서대로 나열해 보여주는데, `--durations=5`처럼 숫자를 주면 가장 느린 5개만 보여주고 옵션을 생략하면 이 목록 자체가 출력되지 않습니다.

```
docker compose run --rm dev pytest -q --durations=5
```

이 규모의 배정 테스트 1개가 계산에 쓴 시간은 0.08초였고, 같은 실행에서 전체 테스트는 약 2초에 끝났습니다. 계산 규모가 실제 운영 크기(2주·합주실 2개·팀 4개)일 때도 응답 대기 시간에 문제가 없는 수준입니다.

### 트러블슈팅

**문제 1 — 실제로는 겹치지 않는 합주실 이름을 겹친다고 오판함**

- **언제**: 합주실 × 날짜 펼치기를 구현하던 중, 방어 차원에서 "생성된 표시가 다른 합주실의 원래 이름과 우연히 같아지는 경우"까지 막는 검사를 추가한 직후
- **어디서**: 합주실 이름에 날짜 꼬리표를 붙이는 부분
- **무엇이 벌어졌나**: 예를 들어 "1번방"이라는 합주실과 "1번방 (2026-08-01)"이라는 합주실이 함께 요청에 들어오면 앞의 합주실이 8월 1일에 만드는 표시("1번방 (2026-08-01)")가 뒤의 합주실의 원래 이름과 글자 그대로 같아집니다. 이 경우를 막으려고 추가한 검사가 이런 입력을 전부 "이름이 겹친다"며 거부했습니다
- **왜 그런가**: 실제로 계산 엔진에 넘어가는 표시는 "1번방 (2026-08-01)"과 "1번방 (2026-08-01) (2026-08-01)"로 서로 다릅니다. 날짜 꼬리표는 길이가 항상 고정이고 합주실 이름은 저장 단계에서 이미 서로 달라야 하는 값이라 2개 합주실의 표시가 실제로 같아질 방법이 없어서, 겹칠 수 없는 경우를 겹친다고 잘못 판단한 오탐이었습니다
- **어떻게 해결했는지**: 이 방어 검사를 삭제했습니다. 실제로 표시끼리 같아지는 입력을 재현할 수 없다는 것을 확인한 뒤, "겹쳐 보이지만 거부되면 안 되는" 입력을 테스트로 남겨 같은 오판이 재발하지 않게 했습니다
- **남는 영향**: 없습니다. 이후 계산 엔진이 이름 대신 저장소의 번호를 그대로 받도록 변경되면서 날짜 꼬리표 자체가 사라졌고, 이 문제가 속한 부류도 함께 없어졌습니다

**문제 2 — 기간이 겹치는 두 요청이 저장 단계에서 500 오류로 노출됨**

- **언제**: 다른 기간이 이미 같은 합주실·같은 시각을 쓰고 있을 때의 동작을 검증하던 중
- **어디서**: 계산이 끝난 배정 결과를 현행 시간표로 저장하는 부분
- **무엇이 벌어졌나**: 두 집중 합주기간의 날짜가 겹치고 같은 합주실을 함께 배정 대상으로 지정하면 저장 시점에 "합주실 + 시작시각" 중복을 막는 제약에 걸렸고, 이 제약 위반이 그대로 처리되지 않고 서버 내부 오류(500)로 드러났습니다
- **왜 그런가**: 저장 계층의 중복 방지 제약은 [데이터 저장소](../../database-layer/README.md)가 이미 정해 둔 검증인데, 이 계층은 그 제약에 위반될 수 있는 상황을 미리 검증하지 않고 있었습니다. 사용자가 실제로 만들 수 있는 입력 실수인데도 그 실수를 안내하는 대신 원인을 알 수 없는 서버 오류로 반환하고 있었습니다
- **어떻게 해결했는지**: 저장 중 이 제약 위반이 발생하면 즉시 롤백하고, "다른 기간이 이미 같은 합주실의 같은 시간을 사용하고 있습니다"는 문구와 함께 사용자 오류로 변경해 응답합니다. 같은 수정에서 요청에 같은 팀·합주실 번호가 중복으로 들어오면 오류 메시지 없이 1개로 합쳐지던 동작도 미리 거부하도록 함께 수정했습니다
- **남는 영향**: 겹치는 기간이 같은 합주실을 함께 지정하는 요청은 이제 사용자 오류로 안내되며, 먼저 저장된 기간의 현행 시간표는 이 실패로 인해 변경되지 않습니다

**문제 3 — 요청마다 데이터베이스 engine을 새로 생성하고 있었음**

- **언제**: 3개 endpoint를 다 만든 뒤 전체를 1번에 검토하던 중
- **어디서**: endpoint가 요청마다 DB session을 받는 부분
- **무엇이 벌어졌나**: 요청이 들어올 때마다 engine(데이터베이스 접속 설정과 connection pool을 가진 객체)을 처음부터 다시 생성하고 있었습니다. engine 1개에는 실제 접속을 2개 이상 보관하는 connection pool(접속 풀)이 있어서 요청이 쌓이면 사용하지 않는 접속이 계속 늘어나고, 결국 데이터베이스가 허용하는 접속 수를 넘겨 서버가 중지됩니다
- **왜 그런가**: engine을 생성하는 함수는 원래 "호출할 때마다 새로 생성한다"는 전제로 작성되었고, 요청마다 호출되는 위치에서 그대로 사용하면서 문제가 발생했습니다. 모든 테스트가 이 함수를 테스트 전용 접속으로 교체하기 때문에 실제로는 1번도 실행된 적이 없어 테스트로는 드러나지 않았습니다
- **어떻게 해결했는지**: engine을 1번만 생성하고 다시 호출할 때는 같은 engine을 반환하도록 변경했습니다. "설정이 없으면 즉시 실패한다"는 기존 규칙은 그대로 유지했고, 2개 동작을 모두 검증하는 테스트를 새로 만들었습니다
- **남는 영향**: 없습니다. 다만 engine이 1개만 존재하게 되었으므로 나중에 접속 주소를 실행 중에 변경해야 할 일이 생기면 그 부분을 다시 검토해야 합니다

**문제 4 — 되돌리기에도 같은 500 오류가 남아 있었음**

- **언제**: 문제 2를 수정한 뒤 전체를 1번에 검토하던 중
- **어디서**: 되돌리기 endpoint
- **무엇이 벌어졌나**: 문제 2에서 배정 endpoint에는 검증을 추가했는데 되돌리기 endpoint에는 추가하지 않아서, 다른 기간이 그 합주실·그 시각을 차지한 뒤에 되돌리기를 호출하면 똑같이 서버 오류가 발생했습니다
- **왜 그런가**: 되돌리기도 같은 table에 이전 시간표를 다시 저장하는 동작이라 배정과 완전히 같은 제약에 위반됩니다. 한쪽만 수정하면 다른 쪽이 남는다는 것을 처음에 발견하지 못했습니다
- **어떻게 해결했는지**: 2개 endpoint가 같은 판별과 같은 안내 문구를 사용하도록 1곳으로 모았습니다. 아울러 문제 2에서 추가한 판별이 다른 원인의 저장 실패까지 같은 안내로 대체하고 있었으므로, 실제로 어떤 상황에서 무엇이 담기는지 컨테이너에서 직접 확인해 판별을 좁혔습니다
- **남는 영향**: 데이터베이스가 반환하는 정보만으로는 "다른 기간이 차지함"과 "같은 기간에 대해 2개 요청이 동시에 저장을 시도함"을 구분할 수 없다는 것을 확인했습니다. 그래서 안내 문구를 2가지 경우 모두에 맞도록 작성했고, 완전한 구분은 미구현입니다

## Conclusion

기간 자동 배정은 저장된 기간·팀·합주실 데이터를 계산 엔진이 요구하는 형태로 펼치고 되돌리는 변환 작업과, 성공한 결과를 즉시 저장하는 연결 작업으로 이루어집니다. 계산의 규칙은 [자동 배정](../../auto-assignment/README.md)에서, 저장의 규칙은 [배정 이력과 롤백](../../database-layer/schedule-versioning/README.md)에서 각각 그대로 사용할 뿐, 이 계층이 새로 만드는 규칙은 날짜·이름을 펼치고 되돌리는 부분과 팀당 slot을 자동으로 정하는 부분뿐입니다.
