## Abstract

합주실과 기간은 "언제, 어떤 규칙으로 합주실을 사용하는가"의 규칙을 정의합니다. 합주실은 기본 1개이며 2개 이상으로 추가할 수 있고, 합주실마다 개방 시간과 폐쇄 시간을 별도로 설정할 수 있습니다. slot(1시간 단위 시간 칸)은 1시간 단위로 고정했습니다. 집중 합주기간으로 지정된 날에는 시스템이 자동으로 slot을 배정하고, 그 밖의 모든 날은 선착순 예약제를 적용합니다. 예약 가능한 기간을 별도로 등록할 필요는 없습니다.

## Introduction

합주실 운영 방식은 밴드마다, 시기마다 다릅니다. 평소에는 필요할 때만 예약하지만, 공연을 앞두면 모든 팀이 균등하게 연습해야 합니다. 이 2가지 상황을 규칙 1개로 통합하면 반드시 한쪽이 불편해집니다. 따라서 Banblit은 집중 합주기간만 등록하도록 하고, 그 기간이 적용되지 않은 모든 날은 선착순 예약제를 적용합니다. 평상시 예약 가능 기간을 별도로 등록하도록 강제하면, 등록을 빠뜨린 날이 누구도 사용할 수 없는 날이 됩니다.

## Description

### 합주실은 1개로 시작하지만 추가할 수 있습니다

기본값은 1개입니다. 다른 밴드에 같은 방식을 제공할 때를 대비해, 합주실을 2개 이상으로 추가하는 작업을 간단하게 설계했습니다. 각 합주실은 고유 이름을 가지며, 이름이 중복되면 설정에서 거절합니다. 같은 이름이면 배정 결과에서 2개 합주실을 구분할 수 없어 같은 합주실에 2개 팀이 배정된 것처럼 표시되기 때문입니다.

개방 시간과 폐쇄 시간은 "합주실 정보 수정" 권한을 가진 사용자가 각 합주실마다 개별로 설정할 수 있습니다.

### slot 단위는 1시간으로 고정했습니다 (2026-09-08)

slot은 **정각에만** 시작합니다. 개방 시간도 정각이어야 하며, 정각이 아니면 거절합니다. 예를 들어 18시 30분에 개방하는 설정은 거절합니다. 정각이 아닌 시간을 오류 메시지 없이 버리면 설정 오류를 아무도 발견하지 못하기 때문입니다.

**30분 단위에서 1시간 단위로 변경했습니다(사용자 결정).** 30분 단위 합주는 실제로 일어나지 않았으므로, 세분화했어도 항상 2개 slot이 함께 배정되었습니다. slot 크기를 절반으로 줄이면 배정 계산이 검토해야 하는 경우의 수도 함께 증가합니다.

slot 길이는 서버의 `SLOT_MINUTES` 상수 1개로만 정의합니다. 변경할 경우 `SLOT_MINUTES` 만 수정합니다. 개방/폐쇄 시간 검증 규칙도 `SLOT_MINUTES` 에서 도출됩니다.

합주실마다 개방 시간이 달라도 slot의 경계는 모든 합주실이 공유합니다. 1번 합주실의 19시 slot과 2번 합주실의 19시 slot은 같은 시간 구간이므로, 1명이 같은 시간에 2개 합주실에 배정되지 않도록 검증할 수 있습니다.

### 기간은 2종류입니다

| 언제 | 사용 방식 | 자동 배정 | 등록이 필요한가 |
| --- | --- | --- | --- |
| 집중 합주기간으로 덮인 날 | 팀마다 같은 개수의 slot을 배정 | 있음 | 집중 합주기간을 등록합니다 |
| 그 밖의 모든 날 | 선착순 예약 | 없음 | 아니오. 아무것도 등록하지 않습니다 |

**예약 가능한 날은 "집중 합주기간이 지정되지 않은 날"입니다(사용자 결정).** 예약을 허용하려고 별도 기간을 등록할 필요가 없습니다. 서버는 예약 요청을 받으면 해당 날짜가 집중 합주기간에 포함되는지만 확인하고, 포함되지 않으면 수락합니다.

집중 합주기간에는 모든 팀이 정확히 같은 개수의 slot을 할당받습니다. 예를 들어 저녁 6시간이 2주간 개방되고 팀이 6개면, 각 팀은 1시간 slot 14개를 배분받습니다. 팀 1개라도 할당량을 채우지 못하면 전체 배정이 실패로 처리되어 헤드매니저가 조율안을 결정합니다. 항상 자동 배분을 원하는 조직은 집중 합주기간에 **"매일" 옵션**을 활성화합니다. 이 옵션이 활성화된 기간은 예약을 차단하지 않으므로, 자동 배정을 실행하면서도 남는 slot은 예약으로 개방됩니다.

팀이 할당받은 slot 외에 남은 slot은 예약 가능한 slot으로 함께 표시되므로, 집중 합주기간 중에도 비어 있는 slot은 예약으로 사용할 수 있습니다.

### 같은 규칙을 3곳에서 검증합니다

합주실·기간 권한 항목을 가진 사용자가 설정 화면에서 값을 입력하면, 화면·서버·데이터베이스가 같은 규칙을 3번 검증합니다.

```
사용자 입력  ──▶  화면이 먼저 검증      : 오류 위치를 즉시 알려주기 위해
                    │
                    ▼
             서버가 경계에서 검증        : 화면을 거치지 않는 요청도 있으므로
                    │
                    ▼
             데이터베이스가 마지막 검증   : 이전 두 계층을 통과한 잘못된 값 방지
```

중복처럼 보이지만 각 계층의 검증 범위가 다릅니다. 화면만 검증하면 서버를 직접 호출하는 요청이 통과하고, 서버만 검증하면 사용자가 저장 버튼을 누를 때까지 오류를 알 수 없습니다. 앞의 2개 계층이 검증하지 못한 값도 데이터베이스 검증이 거절합니다.

이름 중복은 데이터베이스가 마지막에 감지합니다. 2명의 사용자가 동시에 같은 이름을 입력할 경우, 각자 입력 시점에는 같은 이름이 아직 없었으므로 화면과 서버 검증을 모두 통과할 수 있습니다. 서버는 데이터베이스가 거절한 중복을 받아서 사용자가 읽을 오류 메시지로 반환합니다.

개방 시간과 폐쇄 시간, 기간 날짜는 수정할 수 있지만 삭제는 미구현입니다. 삭제하면 이미 생성된 배정과 예약이 함께 삭제되므로, 삭제된 배정과 예약을 어떻게 처리할지 정한 후 삭제 기능을 추가합니다.

### 권한을 가진 사용자만 입력한다는 규칙을 서버가 검증합니다

이전에는 "권한을 가진 사용자만 입력한다"는 규칙을 화면에서만 검증했으므로, 로그인하지 않은 사용자가 서버를 직접 호출하여 합주실을 생성하거나 운영 시간을 변경할 수 있었습니다. 서버가 로그인 session을 직접 관리하면서 이제 각 endpoint(API의 요청 주소 단위)는 권한을 먼저 검증합니다.

| 하는 일 | 할 수 있는 사람 |
| --- | --- |
| 합주실 생성 | "합주실 추가"를 가진 사용자만 |
| 합주실 수정(이름, 개방 시각, 폐쇄 시각) | "합주실 정보 수정"을 가진 사용자만 |
| 기간 생성 | "집중합주 기간 추가"를 가진 사용자만 |
| 기간 수정(종류, 날짜, 배정 계산 시각) | "스케줄링 시간 설정"을 가진 사용자만 |
| 합주실 목록·기간 목록 조회 | 로그인한 사용자 전체 |
| 합주실의 예약 현황 조회 | 로그인한 사용자 전체 |
| slot 예약 | 로그인한 사용자 전체. 예약자는 언제나 본인입니다 |
| 예약 수정·취소 | 그 slot을 예약한 본인, 그리고 "타 멤버 예약 수정 및 취소"를 가진 사용자 |
| 불가능 일정 조회·추가·삭제 | 본인만. 권한 항목을 전부 가진 사용자도 다른 사용자의 불가능 일정은 조회할 수 없습니다 |

예약 소유자는 요청 매개변수의 사용자 이름이 아니라 인증 cookie의 소유자입니다. 이전에는 누구 이름으로 예약할지를 요청에 담아 보냈고 서버가 검증 없이 사용했으나, 현재는 예약자를 선택하는 매개변수 자체가 없습니다.

팀을 지정하는 예약은 해당 팀의 소속 여부를 검증합니다. 이전에는 "그런 팀이 있는가"만 확인했으므로, 소속이 아닌 사용자가 다른 팀 이름으로 slot을 예약할 수 있었습니다. 그 slot이 전체 일정에 해당 팀이 사용한 slot으로 기록되어 일정 정보 자체가 잘못되었습니다. slot 1개가 잘못 예약되는 것을 넘어 전체 일정 정보가 잘못되므로, 이제는 소속이 아니면 거절합니다.

불가능 일정은 권한 항목을 모두 가진 사용자도 다른 사용자의 불가능 일정을 조회할 수 없습니다. 기획 문서에서 일반 멤버의 역할은 "자신의 불가능 일정 관리"로만 정의되며, 배정 계산은 서버가 데이터베이스를 직접 읽으므로 endpoint로 다른 사용자의 불가능 일정을 조회할 필요가 없습니다. endpoint를 개방하지 않으면 다른 사용자의 불가능 일정이 노출될 경로가 없으므로, 조회가 필요한 경우가 생기면 그때 용도와 접근 규칙을 먼저 정합니다.

검증은 서버 테스트 468개 전부와 화면 테스트 202개, 타입 검사 모두가 통과하는 것으로 확인했습니다. 위 표의 권한 분기는 합주실·기간·예약·불가능 일정마다 별도의 테스트 파일이 담당하며, 로그인하지 않은 요청은 401, 로그인했지만 권한이 없는 요청은 403으로 서로 다른 응답을 받는지까지 함께 검증합니다.

## Conclusion

기간 정의가 완료되면 예약과 집중 합주기간 배정 결과는 [스케줄러](../scheduler/README.md)에서 표시되고, 집중 합주기간의 배정 계산 자체는 [자동 배정](../auto-assignment/README.md)이 담당합니다.
