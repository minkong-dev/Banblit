## Abstract

팀과 소속은 "누가 어느 팀에서 어떤 악기를 맡는가"를 다룹니다. 한 사람은 여러 팀에 속할 수 있고, 여러 악기를 다루는 사람은 팀마다 다른 포지션으로 소속될 수 있습니다. 그래서 소속은 사람 하나가 아니라 사람과 팀과 포지션을 묶은 단위로 기록합니다. 팀은 "팀 만들기·이름 바꾸기" 항목을 가진 사람이 만들고, 멤버는 공개된 팀 목록에서 참가를 신청합니다. 신청이 곧바로 소속이 되는지 승인을 받아야 소속이 되는지는 팀마다 고른 승인 방식이 가르고, 승인을 기다리는 사람은 아직 그 팀 소속이 아닙니다.

## Introduction

밴드에서는 한 사람이 여러 팀을 겸하는 일이 흔하고, 기타도 치고 드럼도 치는 사람이 팀마다 다른 악기를 맡기도 합니다. 이런 구조를 담지 못하면 일정 계산이 어긋납니다. 예를 들어 같은 사람이 두 팀에 동시에 배정되면 안 되기 때문에, 소속을 정확히 기록하는 일이 이후 [자동 배정](../auto-assignment/README.md)의 바탕이 됩니다.

## Description

### 소속은 사람이 아니라 세 값의 묶음입니다

소속은 (사람 + 팀 + 포지션) 하나로 봅니다. 같은 사람이 A팀에서는 기타, B팀에서는 드럼을 맡으면 서로 다른 두 소속이 됩니다. 악기 포지션은 정해진 목록에서 고르고, 사람은 가입할 때 자신이 맡을 수 있는 포지션을 체크합니다.

### 팀 참가는 이제 두 갈래로 갈립니다

그동안은 승인 방식을 무엇으로 정해 두든 신청하면 그 자리에서 가입됐지만, 이제 그림의 두 갈래가 실제 동작입니다.

```
멤버가 공개 팀 목록에서 팀 선택
        │
     참가 신청
        │
   ┌────┴──────────────────┐
자동 승인 팀              직접 승인 팀
   │                        │
소속 성립(승인됨)      신청 걸림(대기 중)
                            │
                  ┌─────────┴──────────┐
                승인                  거절 또는 본인이 취소
                  │                        │
             소속 성립(승인됨)         신청이 사라짐
```

팀을 만드는 것도 이름을 바꾸는 것도 "팀 만들기·이름 바꾸기" 항목을 가진 사람이 하지만, 지향점은 멤버가 스스로 팀에 참가하는 것입니다. 참가 승인 방식은 팀마다 자동 승인과 직접 승인 중에서 같은 항목을 가진 사람이 고르고, 이미 있던 팀은 지금까지의 동작이 그것이었으므로 전부 자동 승인으로 시작합니다. 소속 인원 수나 악기 구성에는 제약을 두지 않았습니다.

팀 목록을 읽으면 그 팀의 승인 방식이 함께 담겨 옵니다. 신청 버튼을 누르기 전에 즉시 들어가는 팀인지 기다려야 하는 팀인지 알 수 있어야 하기 때문입니다.

### 대기 중인 사람은 그 팀 소속이 아닙니다

소속에 승인됨과 대기 중 두 상태가 생겼습니다. 대기 중이라는 것이 지금까지 없었으므로 이미 있던 소속은 전부 승인됨입니다.

대기 중인 사람이 소속이 아니라는 것은 표현의 문제가 아니라, 소속을 세거나 훑는 자리 전부에서 실제로 빠진다는 뜻입니다.

| 그 팀에서 | 승인됨 | 대기 중 |
| --- | --- | --- |
| 팀 명단에 나오는가 | 나온다 | 나오지 않는다 |
| 팀 인원 수에 세는가 | 센다 | 세지 않는다 |
| 팀 게시판을 읽고 쓸 수 있는가 | 된다 | 안 된다 |
| 그 팀 이름으로 예약할 수 있는가 | 된다 | 안 된다 |
| 자동 배정이 보는 팀 명단에 들어가는가 | 들어간다 | 들어가지 않는다 |

소속을 세거나 훑는 자리는 서버 전체에 열한 곳이 있고, 그 열한 곳을 모두 찾아 승인된 것만 보도록 맞췄습니다. 한 곳이라도 빠뜨리면 명단에는 없는 사람이 배정에는 들어가는 식으로 어긋납니다.

신청 취소는 팀에서 나가는 것과 같은 자리로 합니다. 대기 중인 자기 신청을 무르는 것은 결국 그 팀과의 관계를 끊는 일이라, endpoint를 따로 만들지 않고 나가는 자리가 상태를 가리지 않고 처리하게 했습니다.

로그인한 사람은 자기 신청 상태를 읽을 수 있습니다. 내 계정을 묻는 자리가 승인된 소속과 대기 중인 신청을 한 목록에 담아 상태로 갈라 주는데, 그러지 않으면 신청해 놓고 페이지를 닫은 사람이 자기가 신청을 냈는지조차 알 수 없기 때문입니다.

같은 신청에 승인과 거절이 겹쳐 들어오면 방금 승인돼 소속이 된 행을 뒤늦게 도착한 거절이 그대로 지울 수 있었습니다. 신청을 찾아내는 자리에 잠금을 걸어 한 번에 하나만 지나가게 했고, 먼저 들어온 쪽이 상태를 바꾸고 나면 뒤늦은 쪽은 찾는 조건에 더 이상 걸리지 않아 "그런 참가 신청이 없다"로 걸러집니다.

### 누가 무엇을 할 수 있는지 서버가 가릅니다

로그인 상태를 서버가 직접 들고 있게 되면서, 팀과 소속을 건드리는 자리마다 권한을 먼저 확인합니다.

| 하는 일 | 할 수 있는 사람 |
| --- | --- |
| 팀 만들기, 팀 이름 바꾸기, 참가 승인 방식 바꾸기 | "팀 만들기·이름 바꾸기"를 가진 사람만 |
| 팀에 참가 신청하기 | 로그인한 사람 — 들어가는 것은 언제나 본인 |
| 팀에서 빼기, 내 신청 취소하기 | 본인, 또는 "팀에서 남을 빼기"를 가진 사람 |
| 참가 신청 목록 읽기, 승인하기, 거절하기 | "팀 참가 승인" 항목을 가진 사람 |
| 팀 목록·팀 명단·포지션 목록 읽기 | 로그인한 사람 전체 |

승인·거절을 가리는 것은 권한 항목 하나입니다. 어떤 항목들이 있고 누가 그것을 갖는지는 [계정과 역할](../accounts-and-roles/README.md)이 정본이고, 여기서는 승인·거절에 그 항목이 필요하다는 것까지만 적습니다. 승인 방식 자체를 바꾸는 것은 팀을 고치는 일이라 팀을 다루는 항목이 가릅니다.

참가하는 사람은 언제나 요청을 보낸 본인입니다. 예전에는 누구를 넣을지 요청에 적어 보내면 서버가 그대로 믿어서, 로그인하지 않은 사람도 남을 아무 팀에나 집어넣을 수 있었습니다. 지금은 인증 쿠키의 주인만 들어갑니다. 남을 대신 넣는 길은 그 화면이 아직 없어서 만들지 않았고, 멤버를 직접 넣는 화면을 만들 때 그 endpoint를 따로 열려고 합니다.

소속을 빼는 것은 본인이거나 "팀에서 남을 빼기"를 가진 사람일 때만 되고, 그 항목이 없는 사람이 남의 소속을 지우려 하면 거절됩니다. 팀을 만들 때 "만든 사람"을 요청에 적어 보내던 자리도 없앴습니다. 만든 사람은 요청에 적힌 값이 아니라 인증 쿠키의 주인이므로 적어 보내는 값은 믿을 근거가 되지 못하고, 화면 쪽에서도 그 값을 보내던 자리를 함께 지웠습니다.

확인은 서버 테스트 457개가 모두 통과하고 타입 검사도 95개 파일에서 이상이 없는 것으로 했습니다. 위 표의 갈림은 팀·소속 endpoint를 확인하는 테스트 파일이 맡는데, 로그인하지 않은 요청과 로그인했지만 권한이 없는 요청을 서로 다른 응답으로 가르는지까지 함께 봅니다. 승인 방식 두 갈래, 대기 중인 사람이 명단·인원 수·게시판·예약·배정 명단에서 빠지는 것, 본인이 자기 신청을 무르는 것도 같은 파일이 봅니다.

저장소를 옮기는 변경이라 데이터를 넣어둔 채로 올렸다 내렸다 왕복해 보았습니다. 되돌리면 대기 중인 신청은 사라지고 승인된 소속만 남는데, 상태 열이 없어지는 순간 대기 중이던 행이 소속으로 둔갑하는 것을 막기 위해 되돌리는 쪽이 그 행들을 먼저 지웁니다.
